# Raw 0.0.39 camera-enabled gameplay performance diagnosis

**Date:** 2026-09-05  
**Bead:** `aerobeat-web-assembly-mi6`  
**Research:** `995bcf62-c7be-4172-a677-2f724e268ab8`  
**Candidate:** immutable raw `0.0.39`  
**Disposition:** Architecture diagnosis complete; target-Bug trace is still required before selecting a CV/compositor optimization.

## Exact Observed Failure

Derrick reports that Flow is smooth on Bug with camera disabled, but enabling camera/tracking materially lowers framerate. It remains playable, but the machine struggles to run gameplay and camera tracking together.

Missing from the original observation: numeric FPS/frame-time distribution, exact camera format, browser/DPR/thermal state, inference timing, and whether “camera off” means no CV or only a hidden live feed.

## Expected Behavior

- Display/gameplay cadence remains independent of CV cadence.
- Measured MediaPipe submissions remain at or below 15 FPS.
- Gameplay uses only current measured poses; no prediction or fabricated input.
- Camera/CV failure, tracking freshness, calibration, privacy, lifecycle, and fallback remain fail-closed.
- Prior practical display floor remains at least 45 FPS on an approximately 60 Hz target, with camera-on at least 90% of paired camera-off measured-play rate.

## Execution Path

1. Production requests unconstrained `{facingMode:"user"}` media; browser chooses width/height/framerate.
2. Production CV runs a timer at `ceil(1000/15)` and directly invokes `createMediaPipePoseAdapter` with the live `HTMLVideoElement`.
3. `PoseLandmarker.detectForVideo(video,timestamp)` is synchronous on the main thread even with the GPU/WebGL delegate.
4. MediaPipe and PlayCanvas can compete for main-thread time and GPU/WebGL capacity.
5. Display rAF consumes each latest measured pose at most once, projects session targets, updates gameplay, and renders.
6. Renderer currently performs two manual PlayCanvas ticks per display opportunity: one for gameplay and another for cursors, even when cursor input is empty.
7. `projectSessionTargets` maps and sorts the complete resolved-event list each display frame.
8. Camera presentation adds a full-screen mirrored CSS video under a transparent PlayCanvas canvas.

## Most Likely Root Cause

A single target-machine root cause is not yet proven.

Conditional leading causes:

1. If camera-off means no camera/CV, synchronous main-thread MediaPipe plus shared WebGL contention is most likely. Unconstrained capture resolution can multiply upload/inference cost.
2. If camera-off means Aero mode while camera/CV remain active but video is hidden, live video decode/composition beneath transparent WebGL becomes the leading differentiator.
3. Two PlayCanvas ticks per rAF are a confirmed avoidable baseline amplifier.
4. Full event-map/sort/projection per rAF is another likely baseline amplifier.

## Alternative Hypotheses

- Presenter DOM work is low likelihood because closed-menu commits are signature-gated.
- Camera compositor cost is not universally dominant: desktop isolation remained near 60 FPS with visible camera and CV.
- Reported CV dropped-frame counters can miss synchronous stalls because timers coalesce while the main thread is blocked.
- Thermal/power throttling, Bug camera format, and DPR remain unmeasured.

## Why Previous Fixes Failed

Prior cadence work correctly decoupled display rAF from the 15 FPS CV submission rate, but synthetic cadence tests did not measure real MediaPipe synchronous slices, GPU contention, live-video composition, full gameplay scene cost, or Bug thermals.

Production also does not use the existing experimental worker/VideoFrame adapter. `requestVideoFrameCallback` exists only as an unused capability check in the production path.

## Unknowns

- Meaning of camera-off baseline.
- Bug camera width/height/framerate and browser/DPR/power state.
- Display p50/p95/max frame interval and missed-vsync count.
- MediaPipe runtime/end-to-end p50/p95/max and pose-age distribution.
- Renderer CPU/GPU duration, draw calls, triangle/object windows.
- Decode/compositor attribution.

## Minimal Reproduction

On Bug, use exact raw `0.0.39`, same song/difficulty/Flow/orientation/viewport/DPR/browser/power state, after warming camera/model/assets. Run repeated 15–20 second `ABCCBA` windows:

- A: render-only Test control, clearly labeled synthetic/non-input.
- B: measured Play in Aero after calibration; camera/CV active, live feed hidden.
- C: same measured Play in Camera; same retained camera/CV, feed visible.

B versus C isolates compositor cost while preserving measured-pose truth. A versus B captures CV plus full measured-play overhead.

## Proposed Verification

Use a local Chrome Performance trace with screenshots disabled and Main, Frames, GPU, Media, Compositor, and WebGL enabled. Retain only bounded aggregates; never export frames, screenshots, raw landmarks, device IDs, or media-internals dumps.

Capture per window:

- display rate and p50/p95/max rAF interval;
- missed frames and >50 ms long tasks;
- CV submitted/pose/drop deltas and fresh-pose consumption;
- pose age and adapter duration aggregates;
- renderer CPU duration;
- sanitized camera width/height/FPS;
- presenter/runtime commit deltas.

Acceptance: camera-on at least 45 FPS and at least 90% of paired Aero measured-play rate; CV submissions no more than 15.01 FPS; each successful pose consumed once; no >500 ms stale-pose safety or privacy/calibration/scoring regression.

## Recommended Fix

1. Profile Bug before changing provider, cadence, capture resolution, or quality.
2. Add only private bounded rolling instrumentation if DevTools cannot isolate the path.
3. Independently remove the confirmed double-render tax: stage gameplay and cursor entities, then perform one PlayCanvas manual tick per display frame. Prove pixel/depth/cursor-clearing/lifecycle parity across modes/orientations/DPR.
4. If synchronous detection correlates with missed frames, benchmark/productize the existing worker adapter using `requestVideoFrameCallback`, one in-flight transferable `VideoFrame`, latest-wins admission before transfer, guaranteed frame close, exact measured timestamp propagation, and no retained pixels. Compare worker GPU against direct GPU because a second WebGL context can worsen contention.
5. If Bug capture is excessive, constrain to the smallest format passing pose/calibration accuracy; begin evaluation at `640×480@30`, not as an unproved shipping default.
6. If renderer work remains material, pre-sort/index resolved events once and window the active timeline instead of sorting the full chart every rAF.
7. If C alone regresses against B, focus on decode/compositor behavior before CV migration; do not blindly upload video into WebGL.

## Phase 5 CODER performance repair evidence (2026-09-05)

### Repairs shipped in source

1. Renderer `48af4340ff74bfed28be44641f89628292a14f1d` / tree `90129f441c1327d22f64fca9e9d84e1fe01de45c` adds `renderGameplayFrameWithCursors`. It stages the complete gameplay scene and current/empty cursor pool before exactly one manual PlayCanvas tick. Browser readback proved zero differing bytes versus the prior two-call result, identical scene/cursor diagnostics, two legacy tick calls versus one staged call, and immediate empty-cursor disable. Flow/Lanes/Grid, fixed/free camera, portrait/landscape, DPR 1/3 (effective cap 2), direct/cross-origin iframe, environment/context restore, depth/layers, pooling, reconnect, and destroy all passed unchanged.
2. Assembly caches a pre-sorted event index by exact resolved-event array identity. Binary center windows plus a static point-query interval tree and explicit live-judgement lookup avoid per-display full-song map/sort/scan. A 6,003-event reversed corpus proved `JSON.stringify` byte and ordering equality against the unindexed reference across Play/Test, no-obstacle/contact truth, far-from-center committed feedback, long Flow intervals, Boxing intervals, boundaries, and the 128-target cap.
3. A 512-sample private rolling recorder measures display intervals p50/p95/max and missed-vsync, renderer CPU, MediaPipe runtime/end-to-end, pose age, CV counts/rate, and sanitized camera width/height/FPS. It accepts no poses, pixels, IDs, or geometry and is absent from public snapshots/events/iframe payloads/persistence.
4. The initial paired trace proved synchronous main-thread GPU MediaPipe was dominant: runtime p95 `175.1–215.4 ms`, display `4.39–5.41 FPS` with CV versus staged render-only `33.0–34.1 FPS`. The existing GPU-worker/VideoFrame path improved display to `14.1–15.9 FPS` but regressed inference to `302.9–347.5 ms` p95 and pose age to `698.3–817.3 ms` p95, violating the 500 ms safety budget; it was rejected.
5. The existing CPU-WASM worker/VideoFrame path removed the second-WebGL contention and materially improved the same paired benchmark from direct-GPU `4.00/4.31 FPS` (Aero/Camera) to `22.42/27.64 FPS`. Worker pose age max remained `454.0/326.3 ms`, no frame was rejected, and accepted/rejected closure plus one-in-flight admission are vendor-enforced. Production now uses that CPU worker with one in flight, latest-frame admission before transfer, exact capture timestamp propagation, measured-current output only, and terminal disposal. No prediction or fabrication was added.

### Final privacy-safe ABCCBA profile

Evidence: `.plans/evidence/2026-09-05-mi6-local-abccba.json`. Six `4 s` windows were run in order A/B/C/C/B/A for a simulated legacy reference and the staged production path; screenshots and trace snapshots were disabled. A was clearly synthetic render-only. B retained the same real measured camera/CV feed with Aero visible. C retained the same feed with Camera composition visible. Camera settings selected naturally as `640×480 @ 30 FPS`; no capture constraint was added.

- Legacy mean A: `21.74 FPS`; staged mean A: `34.25 FPS` (`+57.5%`).
- Legacy mean B: `23.98 FPS`; staged mean B: `33.98 FPS` (`+41.7%`).
- Staged B/A ratio: `99.2%`; all staged camera-on B/C mean: `35.21 FPS`, `102.8%` of paired staged A.
- Staged camera/CV submission: `6.23–7.47 FPS`, below the `15.01` ceiling. Pose-age p95: `247.3–282.4 ms`; max: `277.4–320.0 ms`, below the 500 ms safety boundary.
- Staged display interval p95 was `33.4 ms`; display was `33.88–36.61 FPS`. This headless, 6,000-event/full-scene local stress profile does **not** meet the `>=45 FPS` target, so it is not a target-hardware PASS.
- Camera-visible C was faster than camera-hidden B in this pair; compositor work is not the selected cause and no compositor change was made.
- Since the browser already selected `640×480 @ 30`, and no paired pose/calibration accuracy study exists, production capture remains unconstrained.

Worker evidence: `.plans/evidence/2026-09-05-mi6-worker-benchmark.json` (GPU rejection) and `.plans/evidence/2026-09-05-mi6-worker-cpu-benchmark.json` (CPU selection).
