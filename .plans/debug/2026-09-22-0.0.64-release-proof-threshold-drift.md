# Rejected raw 0.0.64 — release-proof CV threshold drift

## Exact Observed Failure

Independent immutable-release audit rejected the sole raw 0.0.64 build because its machine-readable `aerobeat-release-proof.json` claims:

```json
"productionPoseConfiguration": {
  "thresholds": [0.5, 0.5, 0.5]
}
```

The actual locked runtime profile and routed adapter use detection/presence/tracking thresholds `0.4 / 0.5 / 0.3`. The raw target is append-only and has already been claimed, so it cannot be corrected or rebuilt in place.

Directly observed:

- `src/production-cv-profile.js` owns `minPoseDetectionConfidence: 0.4`, `minPosePresenceConfidence: 0.5`, `minTrackingConfidence: 0.3`;
- `src/service-graph.js` routes those locked fields into the production adapter;
- runtime assembly tests assert execution detail `thresholds detection 0.4 presence 0.5 tracking 0.3`;
- `scripts/build-release.js` independently hardcodes proof thresholds `[0.5, 0.5, 0.5]`;
- raw 0.0.64 faithfully contains that obsolete hardcoded proof value.

## Expected Behavior

The immutable release proof must be a truthful machine-readable attestation of the exact locked production CV route. Detection, presence, and tracking thresholds in the proof must derive from the same authority used to construct the runtime adapter. A release gate must fail if proof metadata and runtime profile drift.

## Execution Path

1. `npm run build-release` invokes `scripts/build-release.js`.
2. The script computes the release source fingerprint and builds the browser artifact.
3. The runtime bundle includes `lockedProductionCvProfile` and `service-graph.js` routing, so it executes `0.4 / 0.5 / 0.3`.
4. After the bundle is built, `build-release.js` constructs `aerobeat-release-proof.json` from a separate object literal.
5. That literal writes obsolete thresholds `[0.5, 0.5, 0.5]` without importing or comparing the locked runtime profile.
6. No existing unit/release test asserts proof-profile equality.
7. The immutable raw therefore passes build policy while carrying a false threshold attestation.

## Most Likely Root Cause

Release proof metadata duplicated production CV constants instead of deriving them from `lockedProductionCvProfile`. The runtime thresholds were changed for mid-song stability, but the duplicate proof literal and a release-proof equality oracle were not updated. This is authoritative-data drift, not a Vite serialization or runtime routing problem.

## Alternative Hypotheses

1. **Runtime still uses 0.5 / 0.5 / 0.5.** Rejected: source routing, source maps, README coherence, and assembly runtime tests all prove `0.4 / 0.5 / 0.3`.
2. **Proof threshold order differs from detection/presence/tracking.** Rejected: historical proof convention and field context use that exact order; all three names are explicit in the locked profile.
3. **The raw manifest was mutated after build.** Rejected: its value exactly matches the current hardcoded builder literal and the raw target has not been edited/rebuilt.

## Why Previous Fixes Failed

The 0.0.64 work correctly fixed playtest regressions and validated runtime CV behavior, but the release audit initially focused on source fingerprints, dependency provenance, MediaPipe/no-WASM policy, and artifact behavior. The manifest's threshold tuple lacked a source-of-truth equality oracle, so a truthful runtime and a false proof could coexist. Re-running ordinary unit/browser gates could not catch it because they did not parse a generated proof against the locked profile.

## Unknowns

- Whether other proof fields duplicate locked profile values and could drift similarly. Resolve by deriving the complete `productionPoseConfiguration` object from one exported mapper and testing exact equality, rather than patching only the tuple.
- Whether historical raw releases contain the same stale attestation. Historical immutable raws must not be changed; this does not affect the required successor fix.

## Minimal Reproduction

1. Read `lockedProductionCvProfile` and form `[minPoseDetectionConfidence, minPosePresenceConfidence, minTrackingConfidence]` → `[0.4, 0.5, 0.3]`.
2. Read `release/raw/0.0.64/aerobeat-release-proof.json` → `productionPoseConfiguration.thresholds` is `[0.5, 0.5, 0.5]`.
3. Compare the arrays; they differ deterministically.

This does not reproduce before a raw proof exists, but a unit mapper/equality oracle can reproduce the builder drift without creating a release.

## Proposed Verification

Before another build:

1. Extract/export a pure proof-profile mapper derived from `lockedProductionCvProfile`.
2. Assert exact object equality for backend/provider/execution/model/version/thresholds/tracking/preset/source/cadence.
3. Assert generated proof configuration uses that mapper, not literals.
4. Verify the rejected raw 0.0.64 remains untouched and documented as rejected.
5. Bump to 0.0.65, regenerate source-bound target evidence, rerun all gates, build exactly one new raw, and independently compare its proof configuration to the locked profile.

## Recommended Fix

Move production pose proof construction into a pure exported function/module that reads `lockedProductionCvProfile`, including `[0.4, 0.5, 0.3]`, and have `build-release.js` consume it. Add a unit oracle that checks the complete mapped object and rejects a mutated threshold tuple. Do not edit or rebuild raw 0.0.64. Mark it rejected immutable evidence, bump to 0.0.65, and repeat the release tail once.
