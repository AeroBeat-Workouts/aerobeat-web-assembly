# Diagnosis — 0.0.89 version-oracle drift after authorized bump

## Exact Observed Failure

After `npm run version:patch` changed only the package version, lockfile top/root versions and index proof meta from 0.0.88 to 0.0.89, `npm test` reached `scripts/validate-shared-hash-provenance.js:52` and stopped: `AssertionError [ERR_ASSERTION]: lev0 release source must use the exact authorized successor version`; actual `0.0.89`, expected `0.0.88`. Preceding immutable-raw, environment/gameplay, Vite allowlist and 197-file package inventory checks passed. No raw 0.0.89 target exists; no release build ran.

## Expected Behavior

Derrick explicitly authorized one new 0.0.89 raw candidate. Release source version, lockfile, HTML proof meta and the exact authorized-version oracle must agree at 0.0.89. Source browser fixtures must exercise and expect that same version while still rejecting an unexpected drawer control. Immutable raw 0.0.88 and the live service remain untouched.

## Execution Path

`npm run version:patch` → `scripts/bump-patch-version.js` increments package and lockfile fields and replaces index meta → `npm test` → `test:unit` → `validate-shared-hash-provenance.js` loads package.json and asserts literal `0.0.88` before owner provenance. `vite.config.js:89` injects the bumped package version into `src/release-metadata.js:22`; standalone browser fixtures with `configFile:false` instead inject literal 0.0.88 and product-shell/mobile-menu expected drawer text also names 0.0.88. That stale fixture data would conceal or fail the new candidate's version display even if the first assertion were bypassed.

## Most Likely Root Cause

The earlier 0.0.88 source-only successor locked seven test-fixture/oracle version literals to that version. The authorized version bump changes product metadata but does not update those tests. Exact evidence: `validate-shared-hash-provenance.js:52` expects 0.0.88; `validate-product-shell-matrix.js:50` and `validate-mobile-gameplay-menu.js:155` expect drawer 0.0.88; four browser fixtures define `__AEROBEAT_PACKAGE_VERSION__` as 0.0.88. Production Vite reads package.json, so this is release-preflight test drift, not a product menu regression.

## Alternative Hypotheses

1. **Unexpected additional version edit:** unlikely; scoped Git diff is exactly four 0.0.88→0.0.89 fields in three version files, and post-bump fingerprint 69cd5a2c… uses ten clean pinned owners.
2. **Source owner/provenance drift:** unlikely as immediate cause; the failing assertion is before `readReleaseDependencyProvenance()` at line 63; direct provenance and release pack policy passed. Recheck after updating the exact oracle.
3. **Another stale fixture contract:** possible; the workspace search found seven script occurrences. Full unit/browser reruns will reveal any missed context.

## Why Previous Fixes Failed

No fix has been attempted. The bump script correctly changed its three owned files but intentionally does not edit manually version-pinned test oracles. Do not rerun the bump (that would produce 0.0.90), weaken the exact-version oracle, or build despite a red gate.

## Unknowns

Whether additional browser snapshots infer a version indirectly. Run focused provenance, mobile menu and direct/iframe shell matrix after a scoped test-only patch, followed by full `npm test` and `npm run test:browser`; check clean owner pins and fingerprint before building.
