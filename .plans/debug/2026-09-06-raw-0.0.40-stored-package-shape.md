# Raw 0.0.40 stored package shape failure

**Date:** 2026-09-06

**Bead:** `aerobeat-web-assembly-htd`

**Scope:** Research/diagnosis only; no production code, raw release, build, serving, publication, or physical-approval change.

**Conclusion:** Confirmed root cause with an isolated real-Chromium reproduction against immutable raw `0.0.40`.

## Exact Observed Failure

Derrick's physical review reported this failure after a BeatSaver download/list refresh:

```text
AeroAuthoringStorageError: Stored package record shape is invalid
code: storage_record_invalid
```

The Bead identifies the path as `persistence.js` `copyRecord` from `listIndexedDbCollections`'s `packageRequest` callback. An isolated Chromium reproduction against raw `0.0.40` reproduced the exact first exception and the follow-on event-handler exception:

```text
AeroAuthoringStorageError: Stored package record shape is invalid
    at storageError (http://127.0.0.1:5173/assets/index.js:104636:16)
    at copyRecord (http://127.0.0.1:5173/assets/index.js:104252:243)
    at http://127.0.0.1:5173/assets/index.js:104057:51
    at Array.map (<anonymous>)
    at packageRequest.onsuccess (http://127.0.0.1:5173/assets/index.js:104057:36)

AeroAuthoringStorageError: Uncaught exception in event handler.
    at storageError (http://127.0.0.1:5173/assets/index.js:104636:16)
    at idbStorageError (http://127.0.0.1:5173/assets/index.js:104632:9)
    at tx.onerror (http://127.0.0.1:5173/assets/index.js:104063:29)
```

Directly observed in the reproduction:

- IndexedDB database `aerobeat-web-content-authoring` remained at version `6`.
- The triggering package row contained both `flowObstacleContract` and `obstacleContract`.
- Their values were respectively `source_geometry_v1` and `prior_obstacle_contract`.
- Loading current raw `0.0.40` produced both page errors above without any malformed asset bytes or quota pressure.

The exact package values from Derrick's browser were not exported, so song/package IDs, hashes, timestamps, and byte payloads remain unknown. Those identities are not needed to identify the failing structural shape: `copyRecord` throws its **shape** error before validating any values or assets.

## Expected Behavior

A browser database created and populated by raw `0.0.39` must upgrade without losing package bytes, hashes, provenance, collection membership, inline/shared assets, or optional source-cache bytes. Historical content should remain listable, exportable, and deletable, while stale load/play reads return the bounded `flow_obstacle_reimport_required` contract. One stale row must not poison a later download or the entire library list.

The v5 storage-only field should be translated from `flowObstacleContract` to the v6 field `obstacleContract`, not retained as an extra property. A successfully upgraded database must contain records accepted by v6's exact-key validator.

## Historical/current comparison

### Raw proof and source pins

- Raw `0.0.39` proof pins `@aerobeat/web-content-authoring` commit `06b024f4848af6377e83598fe54126252ff9aa6a`, tree `e0957b19883918876deafccdbde4ceae91199dff`.
- Raw `0.0.40` proof pins later commit `5a2fb2e26b5c4dffd1d624c4806bb5c83d31c039`, tree `7221fc5379cea44649dae4870a366ebfaabc41a4`.
- The relevant schema/naming transition is commit `403f1e2`; `403f1e2..5a2fb2e` does not change `src/persistence.js`, so the raw `0.0.40` sourcemap carries the same persistence behavior.
- Raw `0.0.39` `assets/index.js.map` source 778 embeds the v5 implementation; raw `0.0.40` source 779 embeds the v6 implementation. Both maps have complete `sourcesContent`.

### Database version, record keys, names, and values

| Concern | Raw 0.0.39 / `06b024f` | Raw 0.0.40 / `403f1e2` behavior |
|---|---|---|
| IndexedDB version | `5` | `6` |
| Namespace | `aerobeat.authored-packages.v2` | unchanged |
| Package base keys | `key`, `package`, `packageHash`, `assets`, `sourceCache`, `createdAtMs`, `schemaVersion`, `writeToken` | unchanged |
| Optional shared-asset key | `assetRefs` | unchanged |
| Orientation key/value | `flowCellOrientation`: `aerobeat_top_left_v1` or `beatsaber_bottom_left_legacy` | unchanged |
| Contract key | `flowObstacleContract` | `obstacleContract` |
| Current contract value | `source_geometry_v1` | `normalized_obstacle_v2` |
| Legacy contract value | `bounded_mask_v1` | `prior_obstacle_contract` |
| Collection base keys | `collectionId`, `songName`, `sourceProvider`, `sourceId`, `sourceVersionHash`, `converterProfileId`, `converterProfileHash`, `modifierIds`, `packageKeys`, `packages`, `createdAtMs`, `schemaVersion`, `writeToken` | unchanged |
| Package/collection stable identities | package `key`, collection `collectionId`, `packageKeys`, and per-difficulty `packages[].packageKey` | unchanged; reimport is intended to replace stable keys |

A normal v5 downloaded package with shared audio has exactly these storage keys:

```text
key, package, packageHash, assets, sourceCache, createdAtMs, schemaVersion,
writeToken, assetRefs, flowCellOrientation, flowObstacleContract
```

A normal v5 downloaded collection has its 13 base keys plus:

```text
flowCellOrientation, flowObstacleContract
```

The v6 migration currently uses object spread:

```js
cursor.update({
  ...value,
  sourceCache: Array.isArray(value.sourceCache) ? value.sourceCache : [],
  writeToken: typeof value.writeToken === "string" ? value.writeToken : "",
  schemaVersion: authoringDatabaseVersion,
  flowCellOrientation: event.oldVersion < 4
    ? legacyFlowCellOrientation
    : (value.flowCellOrientation ?? correctedFlowCellOrientation),
  obstacleContract: legacyObstacleContract
});
```

Because `...value` copies the old key and no code deletes it, DB5→DB6 produces this exact invalid package shape:

```text
key, package, packageHash, assets, sourceCache, createdAtMs, schemaVersion,
writeToken, [assetRefs], flowCellOrientation,
flowObstacleContract, obstacleContract
```

The equivalent collection row also retains both contract keys. The v5 value may be either `source_geometry_v1` or `bounded_mask_v1`; v6 adds `obstacleContract: "prior_obstacle_contract"` in both cases. The common raw `0.0.39` newly downloaded row carries `source_geometry_v1`.

Current `copyRecord` accepts only six exact alternatives: base/ref records, optionally with orientation, optionally with **only** `obstacleContract`. `exactRecord` requires the own-key count to equal the expected list. Therefore the extra enumerable `flowObstacleContract` property deterministically triggers `Stored package record shape is invalid` before value, hash, package, asset, or quota checks. `copyCollection` has the same dual-key defect waiting behind the package scan.

## Execution Path

1. Raw `0.0.39` writes DB version 5 package and collection rows with `flowObstacleContract` using `putCollection`. Downloaded package rows use stable package keys and `assetRefs` to content-addressed shared audio.
2. Raw `0.0.40` opens the same named database with requested version 6.
3. `onupgradeneeded` receives `oldVersion === 5` and cursor-updates every package and collection.
4. The updates spread each old row, preserving `flowObstacleContract`, then add `obstacleContract: "prior_obstacle_contract"` and `schemaVersion: 6`.
5. The upgrade commits. The browser database is now physically version 6 and contains dual-key records.
6. Every later current-code open requests version 6. IndexedDB does not fire `onupgradeneeded` when requested/current versions are equal, so no migration or repair runs again.
7. Assembly calls `refreshLibrary` at connection and intends to call it again after conversion/import. It starts `authoring.listPackages()`, `authoring.listCollections()`, and `estimateStorage()` together. Separately, a new `putCollection` also scans all package rows in `garbageCollectIndexedDbAssets`, so the same historical row can abort a new persistence transaction before the intended post-import refresh; the user-observed and reproduced stack below is specifically the list path.
8. `listCollections()` reaches `listIndexedDbCollections`; its `packages.getAll()` success callback maps each row through `copyRecord`.
9. `copyRecord` rejects the dual-key row by exact own-key count and synchronously throws `AeroAuthoringStorageError("storage_record_invalid", "Stored package record shape is invalid")` from the native IndexedDB event callback.
10. That uncaught callback exception aborts/errors the transaction. Its `tx.onerror` reports the browser's `Uncaught exception in event handler.` through `idbStorageError`.
11. The assembly `refreshLibrary` promise rejects. UI-originated BeatSaver import has an outer `.catch(error => this.handleError(error))`, but that promise handler cannot catch the original synchronous exception at the native `IDBRequest.onsuccess` event boundary; Chromium therefore reports it as uncaught. The connection-time call is also invoked as `void this.refreshLibrary(...)` without a local rejection handler.

A new BeatSaver download is an action that re-exposes the poisoned database through persistence GC and/or the intended list refresh; it is not the source of the historical invalid row. The invalid shape was created by the earlier DB5→DB6 schema upgrade.

## Most Likely Root Cause

**Confirmed:** the DB5→DB6 migration renames a strict storage field by adding the replacement but does not remove the obsolete field. Exact-record validation then rejects its own migration output, and the database version bump prevents a retry once the malformed rows are committed.

Evidence:

1. Raw `0.0.39` proof and sourcemap establish DB5 plus `flowObstacleContract` storage rows.
2. Raw `0.0.40` proof and sourcemap establish DB6 plus `obstacleContract`-only accepted shapes.
3. Source diff `06b024f..403f1e2` shows the database version and field/value rename together.
4. The v6 upgrade code spreads old values and adds the new key without destructuring/deleting the old key.
5. `exactRecord` rejects extra own properties by key count.
6. Real Chromium loaded a seeded post-migration dual-key v6 record and reproduced the exact raw stack.
7. The same isolated record retained valid `Uint8Array` shared-asset bytes and tiny usage, ruling out asset representation and quota.

## Alternative Hypotheses

1. **Quota exhaustion — contradicted.** Quota paths map to `quota_exceeded`, not `storage_record_invalid`. The reproduction uses three shared-asset bytes and still fails at exact-key validation.
2. **Missing/corrupt shared audio or cover assets — contradicted for this symptom.** Missing referenced shared assets fail later in `resolveRecordAssets` as `Stored shared asset is unavailable`; malformed asset rows have distinct `Stored shared asset shape/values are invalid` messages. The observed throw occurs before asset resolution.
3. **The newly downloaded package is malformed — unlikely/contradicted.** Current writes are normalized by `copyCollectionBatch` before IndexedDB. The failing stack scans all stored packages; a pre-existing dual-key row is sufficient. The exact Chromium reproduction needs no network or new package bytes.
4. **Package payload/hash is invalid — contradicted for the exact message.** Those checks produce `Stored package record values are invalid` or package canonical/size messages after shape acceptance. The observed message is the earlier shape branch.
5. **Only a collection row is invalid — secondary, not the observed first failure.** DB5→DB6 also creates dual-key collection rows, but the reproduced and reported first exception is from `packageRequest`/`copyRecord`. Fixing only packages would expose `Stored collection shape is invalid` next.

## Why the Previous Test Missed It

The existing oracle `scripts/validate-persistence-collections-indexeddb.js` passes:

```text
IndexedDB collection persistence and non-destructive DB4→6 Flow obstacle-contract migration validation passed.
```

It seeds a database directly at version 4 and then opens it at version 6. Its DB4 package and collection fixture rows include `flowCellOrientation` but do **not** include the v5 storage field `flowObstacleContract`. Consequently the v6 spread has no obsolete key to retain, and adding `obstacleContract` creates a valid exact shape.

This proves DB4→DB6 only. It does not model the real sequential browser history DB4→DB5 under raw `0.0.39`, followed by DB5→DB6 under raw `0.0.40`, nor does it seed an already-version-6 post-upgrade row containing both names. The test's version jump bypasses the exact intermediate schema that causes the defect.

- It is unknown whether Derrick's browser also contains older `bounded_mask_v1` rows alongside `source_geometry_v1` rows. Both migrate to the same dual-key structural failure.

5. Seed the equivalent dual-key collection and a valid three-byte shared asset.
6. Navigate to raw `0.0.40` `index.html` and collect Playwright `pageerror` events.
7. Observe the exact `copyRecord` / `packageRequest.onsuccess` stack followed by `Uncaught exception in event handler.`

The executed reproduction recorded the package own keys as:


## Proposed Verification

Before implementation is accepted, add a real-Chromium sequential-schema oracle and a lower-cost IndexedDB regression:

1. Seed **exact DB5** package and collection rows as emitted by `06b024f`, including shared audio, inline asset/source-cache bytes, stable package/collection keys, `flowCellOrientation`, and both old contract values across fixtures.
2. Open them through current code, not a test-authored version-6 repair.
3. Inspect raw DB6 records and require that obsolete `flowObstacleContract` is absent, `obstacleContract` is present with the intended stale value, and package/hash/asset/source-cache/collection membership bytes are unchanged.
4. Verify list, export, delete, and reimport with stable keys. Historical load/play must return `flow_obstacle_reimport_required`; corrected reimport must load.
5. Keep one already-version-6 dual-key fixture to cover browsers already poisoned by raw `0.0.40`; verify bounded repair/quarantine executes even though `onupgradeneeded` does not.
6. Trigger a current package download/write while the historical row exists and require atomic success or bounded failure, a usable list, and zero `pageerror`, `unhandledrejection`, console warning, or console error.
7. Include package and collection variants with and without `assetRefs`, and `source_geometry_v1` plus `bounded_mask_v1`.

This matrix distinguishes the leading migration-shape hypothesis from quota, assets, and new-download hypotheses.

## Minimal Recommended Fix

Implementation is explicitly out of scope here. The smallest complete repair should nevertheless address both creation and already-deployed state:

1. **Correct DB5→next-version migration output:** reconstruct package and collection records from explicitly allowed fields (or explicitly omit `flowObstacleContract`) before writing `obstacleContract`; do not use an unfiltered spread for a renamed exact-shape field.
2. **Repair browsers already at DB6:** bump the database schema version once and migrate/quarantine the exact known dual-key package and collection shapes, or run an equally atomic, one-time transactional repair keyed by durable metadata. Merely changing the existing `oldVersion < 6` code cannot run for an already-v6 database.
3. **Preserve evidence:** retain package bytes, package hash, inline/shared asset bytes, source-cache bytes, write token, timestamps, orientation, stable package/collection identities, and membership. Translate either old contract value conservatively to `prior_obstacle_contract`; do not claim normalized v2 provenance for old package bytes.
4. **Bound event errors:** native IDB request callbacks must catch shape exceptions and reject/abort the owning promise transaction deliberately so malformed/quarantined rows cannot generate uncaught page errors or leave promises unsettled. Library listing should not let one bounded historical row poison management of all valid rows.
5. **Cover both stores:** package-only repair is incomplete because collection rows have the same retained alias.

Regression risks: weakening exact-record validation, silently relabeling stale content as current, losing shared assets during GC, breaking stable reimport replacement, or turning one known historical alias into acceptance of arbitrary extra keys. Prefer an exact one-time migration for the known v5 alias over broadly relaxing current record validation.
