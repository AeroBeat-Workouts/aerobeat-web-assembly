# 0.0.68 successor version oracle

## Exact Observed Failure

`npm test` at the intentionally bumped `0.0.68` source stage failed in `scripts/validate-shared-hash-provenance.js:52`:

```text
AssertionError [ERR_ASSERTION]: lev0 release source must use the exact authorized successor version
'0.0.68' !== '0.0.67'
```

Direct observation: package, lockfile, and HTML proof metadata were advanced together to `0.0.68`; the validation oracle still contains the literal predecessor version `0.0.67`.

## Expected Behavior

The release-source provenance oracle must authorize exactly the single intended successor version, `0.0.68`, after the controlled patch bump and before the append-only raw build. It must continue rejecting all other versions.

## Execution Path

1. `npm run version:patch` invokes `scripts/bump-patch-version.js`.
2. The script atomically advances `package.json`, `package-lock.json`, and the HTML release-proof meta from `0.0.67` to `0.0.68`.
3. `npm test` invokes `npm run test:unit`.
4. `test:unit` invokes `scripts/validate-shared-hash-provenance.js`.
5. That script reads the now-consistent package/lock metadata, then compares `packageJson.version` against a fixed `"0.0.67"` authorization literal.
6. The stale literal rejects the intended source stage before dependency provenance validation continues.

## Most Likely Root Cause

The exact-version assertion is deliberately manual release authorization and is not modified by `bump-patch-version.js`. The authorized-successor literal was not advanced after the controlled version bump. Evidence is the direct comparison at line 52 and the three synchronized `0.0.68` version-bearing files.

## Alternative Hypotheses

1. **Partial version bump** — contradicted: package, lock root/package entry, and HTML proof meta all changed to `0.0.68` in the same bump.
2. **Accidental second bump** — contradicted: predecessor is `0.0.67`, requested successor is `0.0.68`, and the bump output reports exactly `0.0.68`.
3. **Dependency provenance drift** — not reached; failure occurs before pin/status checks and all pinned repos were previously clean and exact.

## Why Previous Fixes Failed

No fix was attempted. The first post-bump full test exposed the intentionally separate manual authorization gate. Earlier source tests correctly passed at `0.0.67`; they could not validate the future version until the controlled bump occurred.

## Unknowns

No material unknown remains for this failure. The subsequent full test will establish whether any additional release-stage oracle requires advancement.

## Minimal Reproduction

From the accepted clean `0.0.67` source stage:

1. Run `npm run version:patch`.
2. Run `node scripts/validate-shared-hash-provenance.js`.
3. Observe the exact `0.0.68 !== 0.0.67` assertion.

The failure does not occur before the version bump.

## Proposed Verification

First inspect the synchronized version values and the single literal comparison. After advancing only the authorization literal to `0.0.68`, rerun `node scripts/validate-shared-hash-provenance.js`, then full `npm test`, build, and diff checks. This distinguishes stale authorization from partial bump or dependency drift.

## Recommended Fix

Advance the exact authorized successor literal in `scripts/validate-shared-hash-provenance.js` from `0.0.67` to `0.0.68`. Do not generalize or derive it dynamically: the hard-coded value is the fail-closed release authorization. Retest the full release-source matrix before committing and building the one append-only raw successor.
