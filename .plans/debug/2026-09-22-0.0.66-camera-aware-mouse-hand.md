# 0.0.66 camera-aware mouse-hand diagnosis

## Exact Observed Failure

Independent QA reproduced a normal Visual Test workbench sequence: author the free-fly camera while Mouse hand is Off, select Left or Right, then move the pointer. Selection correctly preserves and suspends the authored camera pose, but the wrist/equipment anchor does not remain under the pointer. Existing green tests compare normalized equipment records, not screen-space coincidence.

Observed path:

- `normalizedTestEquipmentPointer()` maps the full canvas CSS rectangle directly to `[0,1]²`.
- `handleTestEquipmentPointerMove()` latches that result and rerenders.
- `testEquipmentInput()` substitutes it for the selected synthetic wrist.
- Renderer maps normalized evidence to fixed world coordinates `{x:-2+4x, y:2.5-3y, z:0.45}`.
- No live camera projection participates.

## Expected Behavior

For a finite pointer whose camera ray intersects the visible equipment plane inside canonical gameplay bounds, the selected wrist anchor must project back to that same canvas CSS point within a small tolerance under default or valid authored debug-camera poses. Invalid, clipped, parallel, behind-camera, or out-of-grid intersections fail closed and preserve the previous valid latch.

## Execution Path

1. Canvas pointermove supplies viewport-relative client coordinates.
2. Renderer resolves its own canvas CSS content/client rectangle and active camera viewport.
3. PlayCanvas constructs live-camera near/far points through that screen point.
4. Renderer intersects the ray with world plane `z=0.45`.
5. Renderer rejects invalid/non-visible/out-of-grid intersections.
6. Renderer inverts the canonical outer grid transform: `x=(worldX+2)/4`, `y=(2.5-worldY)/3`.
7. Assembly updates the private latch only for a non-null bounded result and rerenders.

## Most Likely Root Cause

The implementation conflates canvas-relative CSS percentages with gameplay-grid percentages. Those coordinate spaces are not equivalent; the camera projection and viewport lie between them. Free-fly movement makes the stale assumption obvious, but the canonical grid is not guaranteed to occupy the entire viewport even at default pose/aspect.

## Alternative Hypotheses

1. **DPR/backing-store mismatch:** rejected as root cause. PlayCanvas `screenToWorld()` consumes graphics-device client-rectangle CSS coordinates; multiplying by DPR would add error.
2. **Camera continues moving after selection:** rejected. Renderer suspension clears capture/motion while intentionally retaining pose.
3. **Wrong equipment Z:** not the current cause. Cursor/equipment anchors consistently use `z=0.45`.
4. **Reset camera on selection:** rejected. It destroys the authored inspection view and still does not make full-canvas normalization geometrically correct at every aspect/FOV.
5. **Iframe/shadow coordinates:** rejected as primary cause. Client coordinates and bounds are local to the same child document in direct and iframe contexts.

## Why Previous Fixes Failed

The initial diagnosis recorded non-default-camera coincidence as an uncertainty but accepted whole-canvas normalization for the first implementation. Suspending camera input solved ownership conflicts only. Tests proved clamping and selected-hand isolation but did not compare the rendered root anchor or role pixels to the pointer.

## Unknowns

- QA's exact ad-hoc moved pose/error magnitude was not recorded. Deterministic loaded poses will replace this unknown in the oracle.
- Future non-full camera rectangles are not currently used, but supporting `camera.rect` is inexpensive and prevents another projection assumption.

## Minimal Reproduction

1. Start Visual Test and enable equipment preview.
2. Keep Mouse hand Off and translate/rotate the free-fly camera while the equipment plane remains visible.
3. Select Left or Right; confirm pose remains unchanged.
4. Move the pointer to a visible in-grid point.
5. Current behavior moves the wrist by whole-canvas percentages rather than positioning its projected anchor beneath the pointer.

A centered pointer at a symmetric pose can mask the error; an off-center pointer or moved camera reveals it.

## Proposed Verification

- Renderer API oracle: project known in-grid anchors to CSS with `worldToScreen()`, call the new query, and require round-trip normalized axes within `1e-5` at default and moved poses, portrait/landscape, DPR 1/3, and a non-full camera rect.
- Negative rows: non-finite inputs, detached/destroyed/context-lost/zero geometry, outside camera viewport, parallel/behind/clipped plane, and out-of-grid intersections return `null`.
- Browser/world proof: under default and deterministic moved poses, the real equipment root anchor projects within 1 CSS px of the requested point while camera pose remains unchanged.
- Framebuffer proof: baseline-subtracted role-colored marker centroid remains within 2 CSS px with nontrivial pixels; do not use saber blade centroid because the blade extends intentionally from the wrist.
- Assembly retains the previous valid latch after a null projection.

## Recommended Fix

Add one synchronous private renderer query:

```js
projectDebugEquipmentAnchor(clientX, clientY) // frozen {x,y} | null
```

It reads only renderer-owned canvas/live camera, uses PlayCanvas `screenToWorld()` near/far points, intersects `z=0.45`, enforces camera viewport/clips/front-facing/grid bounds, inverts the exact grid transform, snaps epsilon-only boundary drift, and returns null on lifecycle/geometric failure. It never mutates camera/render/input state or enters `describe()`, telemetry, snapshots, bridge, events, storage, persistence, logs, or YAML.

Assembly replaces obsolete full-canvas normalization with this renderer query and latches only non-null results. No assembly fallback retains the incorrect mapping. Lifecycle reset and camera-input suspension remain unchanged.
