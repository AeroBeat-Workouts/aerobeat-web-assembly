## Exact Observed Failure

## Expected Behavior

A Test action must remain explicit and generation-consistent across every asynchronous content/menu operation:

- clicking Test emits `session-test`, chooses `visual_test`, acquires audio only, seeks zero, creates a fresh gameplay generation, and enters `playing/visual_test`;
- no camera, CV, input reset, calibration state, T-pose cue, countdown, scoring, or persistence may appear;
- an earlier Gameplay/Difficulty/Song/Conversion selection may settle before the run starts, but may never commit a second, stale run configuration after that start;
- Start remains the only action that enters `play` calibration and camera/CV acquisition;
- completion remains terminal between-run truth; menu close adds no implicit resume;
- mode-only recovery cannot leave `activeAction=test` paired with `session.purpose=play`.

## Causal Execution Path

1. Audio natural end sets production audio to `stopped@duration`. The display frame advances a playing Visual Test with a non-playing ended clock; gameplay publishes `completed/visual_test`.
2. Assembly reconciles the completed generation once, stopping display/CV/video and releasing the lease without mutating terminal gameplay truth.
3. Opening the menu correctly records `menuDisposition="terminal"`; it does not pause/resume the completed coordinator.
4. A native Gameplay radio emits `gameplay-mode-select` (`src/index.js:1772-1774`) and starts `selectGameplayAxes()` without retaining/awaiting that promise at the action boundary.
5. `selectGameplayAxes()` resolves a variant and returns `selectVariant()` (`484-492`).
6. `selectVariant()` snapshots `futureOnly` **before** awaiting the asynchronous content selection (`465-479`). Because terminal `completed` is absent from its safe-state list, `futureOnly=false`.
7. Before that await resolves, Test emits the correct `session-test`; `handleUiIntent()` correctly routes it to `startFromMenu("visual_test")` (`1746-1751`). There is no label or action inversion.
8. `startSession("visual_test")` creates a new assembly generation, stops media, seeks zero, configures content, leases audio only, invokes gameplay `requestStart(...visual_test)`, and reaches `playing/visual_test` (`242-293`).
9. The older Gameplay-selection promise then resolves. It does not carry or test an assembly-session generation and is not in a tail awaited by `startFromMenu()`/`startSession()`.
10. `selectVariant()` executes its stale continuation: `configureGameplayFromContent(false)`.
11. Gameplay `configureContent()` is intentionally a between-run full configuration API: it clears run truth, sets `sessionPurpose="play"`, `state="calibrating"`, `pauseReason="calibration_required"`, and increments gameplay generation (`session-coordinator.js:140-164`). It therefore overwrites the newer Visual Test generation.
12. Assembly bookkeeping is not changed by that late continuation, leaving the impossible split state `activeSessionAction="test"` versus gameplay `purpose="play"`.
13. `transientCue()` suppresses calibration only when the gameplay session purpose is `visual_test`; it truthfully displays T-pose for the now-current `play/calibrating` coordinator (`src/index.js:1937-1943`). The Test transport independently requires both `activeSessionAction=test` and `session.purpose=visual_test`, so it becomes inactive (`1025-1033`).
14. Subsequent mode/menu activity operates on Play calibration/tracking state and cannot infer the lost Test intent. Opening that Play state resets calibration; close/resume can produce `paused_tracking`, explaining the observed non-recovery.

## Confirmed Root Cause

**An unowned asynchronous Gameplay-selection continuation can commit after a newer explicit session start.** Assembly serializes Test transport, menu pause, and terminal reconciliation, and separately tracks library selection, but does not serialize Gameplay/Conversion/variant selection against Start/Test. `selectVariant()` computes a terminal `futureOnly=false`, awaits content, then performs an unconditional full gameplay configuration. A fast Test click wins temporarily; the older selection then wins last and resets the coordinator to Play calibration.

This is an ordering/ownership defect at the assembly intent boundary, not a calibration algorithm defect.

Evidence that makes this conclusive:

- the UI click and emitted intent are exactly Test/session-test;
- `startSession` receives `visual_test` and reaches `playing/visual_test` generation 4;
- only the older `selectVariant` resolution precedes the transition to generation 5 `calibrating/play`;
- the failed Test starts neither camera nor CV and does not reset input;
- delaying Test until selection settlement recovers correctly;
- all 12 Test combinations fail identically and all 12 Start comparisons retain expected Play calibration semantics;
- immutable sourcemap source is byte-identical to inspected current source.

## Classification of the T-pose Symptom

- **True calibration startup?** The gameplay coordinator is truly in `play/calibrating`, so the overlay is not fabricated. But it is **not** a legitimately requested Play startup: no Start action, camera request, CV start, or Play resource acquisition occurred.
- **Stale overlay?** No. The cue derives from current coordinator state. The stale object is the late content-selection continuation, not the DOM overlay.
- **Action misrouting?** No. Test emits `session-test` and routes to `visual_test` exactly.
- **Button label/state mismatch?** The label and emitted action match. After failure, UI state does become internally contradictory (`activeAction=test`, gameplay purpose=play), which is a downstream symptom.
- **Completed-session resume path?** No. A fresh Visual Test generation is successfully created first. The late full `configureContent` overwrites it afterward.

## Alternative Hypotheses

1. **Stale asynchronous Gameplay selection — confirmed.** Exact event order, controlled delay, generation transition, cross-product reproduction, and stable-after-settlement recovery all isolate it.
2. **Completed state treated as normal pause/resume — contradicted for this defect.** The prior raw-0.0.39 bug was repaired: terminal menu disposition, zero close deltas, stopped audio, and lease reconciliation are correct before the race.
3. **Start/Test UI inversion — contradicted.** DOM label, `data-intent`, emitted intent, `startFromMenu` argument, and `startSession` purpose all agree.
4. **Stale calibration overlay — contradicted.** Gameplay snapshot is currently `play/calibrating`; cue rendering follows that state.
5. **DB7 migration or imported Dub-I-Dub corruption — contradicted as cause.** Physical DB7 migration/import passed, and the failure reproduces without persistence or provider data.
6. **Audio rewind/ended defect — contradicted as trigger.** The session is correctly completed before the mode/action race. No rewind occurs on the failing fresh Test path; audio was stopped then sought to zero.
7. **Calibration/input service spontaneously requested reset — contradicted.** Failed Test rows have zero new CV/camera calls and no Test-side input reset. Input invalidation is inherited service state; the coordinator is reset by `configureContent()`.
8. **Retained-camera Play replay calibration reuse — adjacent unknown, not this failure.** It deserves later contract coverage but cannot explain Test intent reaching Visual Test and then being overwritten by a late variant commit.

The raw-0.0.39 terminal repair correctly fixed a different chain: terminal menu pause/resume → production audio rewind → `audio_clock_rollback`. It established terminal disposition, exact-end transport restart, and resource reconciliation, but assumed all content-changing work was settled before a fresh run command.

The exact 36-row terminal oracle passed because its Cartesian-product name overstates its intent coverage:

## Smallest Recommended Fix

Introduce one assembly-owned serialized **content/variant intent tail** (or equivalent tokenized intent coordinator) shared by Gameplay, Conversion, modifiers, Song, Difficulty, and Start/Test:

- register each async selection operation before yielding;
- make `startFromMenu`/`startSession` await the exact latest selection intent before choosing/configuring content and incrementing the accepted run generation;

The smallest safe conceptual change is serialization at assembly's asynchronous intent boundary. Gameplay, audio, UI, input, and calibration service contracts are behaving correctly given the calls they receive.

## `hxxs` corrective diagnosis and implementation (2026-09-07)

Inspection covered every continuation after `requestResources`, not only the first stale check. A successful lease could be followed by stale ownership or failure at lease publication, camera acquisition/result, retained-camera attachment, `video.play()`, CV startup, final lease publication, or gameplay `requestStart()`. Audio activation rejection can also occur after the video lease half activates. The common defect was the absence of one transaction-wide “committed session” boundary and exact acquisition identity; per-await stale returns could quiesce UI while leaving coordinator ownership or camera/CV/video side effects.

The minimal correction records the coordinator generation returned by the exact Start/Test acquisition, marks the session committed only after current-owner gameplay `requestStart()` succeeds, and compensates in `finally` for every earlier stale return or throw. `releaseOwnedGeneration()` serializes rollback through the existing coordinator queue and releases only when participant plus exact generation still own the lease; a later legitimate transfer or same-participant acquisition makes it a no-op. Release callback failure preserves the first operation error while still removing stale coordinator ownership. Action-created camera streams are released only when they differ from the retained pre-action stream; CV/audio are stopped and video paused only for an uncommitted action that acquired or partially activated resources. Existing committed sessions and later winning actions are not rolled back.

Deterministic Chromium coverage now holds fake `audio.activateLease()` after Test and Start enter acquisition. It covers profile and content-selection invalidation, Test→Start action supersession, audio activation rejection including Start's partial video-lease activation, camera rejection, `video.play()` rejection, CV rejection, delayed disconnect/destroy/reconnect, exact final idle lease/resource state, no stale retained camera/CV/audio/video state, and final-action ownership.
