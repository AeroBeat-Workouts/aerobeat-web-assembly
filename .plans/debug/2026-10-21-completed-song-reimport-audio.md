# Completed-song Reimport: stale transport and unconfirmed audio-only playback

## Exact observed failure
Derrick's signed 0.0.140 Glitch Play: after finishing the same Linkin Park song and selecting Reimport, music began unprompted, camera shifted, beat timeline did not advance and no targets moved; Play/Pause appeared inconsistent. His physical report is accepted as an observation. An isolated pinned 5e scored Play completed naturally with real signed audio/game graph (test-owned calibration pose, not physical CV), then clicked only selected Reimport: direct and cross-origin iframe, at completion and +2/+10 s had **no** new WebAudio source.start or HTMLMediaElement.play, no lease, audio READY/clock stopped at 0, camera/preview paused. Equivalent pinned 5e/5c4c Visual Test completion in direct/iframe also produced no unsolicited media. Exact physical audio autoplay is therefore **not yet reproduced**. But all tested completed Play/Test paths did reproduce stale session intent: session reset to `calibrating/play` timeline 0 with `sessionStartRequested=true`, `activeSessionAction='start'` or `'test'`, while menu is terminal/open and audio is ready/stopped. Evidence: `/tmp/aerobeat-nlru-signed-play-evidence.jsonl` and `/tmp/aerobeat-nlru-signed-evidence-10s.jsonl` (QA script `scripts/diagnose-signed-completed-reimport-browser.js`).

## Expected behavior
Successful selected Reimport should leave the freshly authored song selectable and stopped; only an explicit subsequent Play/Test/Preview starts audio or camera. Transport must not remain armed for the completed former run. Failed Reimport must not delete the old collection or start playback. No new visible message is approved.

## Execution path
`reimportSelectedLibraryCollection` validates the selected BeatSaver source, converts/persists safely, then `convertAcquired` refreshes library and invokes `selectLibraryPackage`. That calls `performSelectContent`, which replaces content, decodes new audio, calls `configureGameplayFromContent(false)`, syncs content playback and publishes; it does NOT retire `sessionStartRequested` or `activeSessionAction`. `configureGameplayFromContent` treats a reimported same package ID as `newSong=false`, so its different-song retirement branch does not clear those flags. `visualTestTransportSnapshot` sets `active` from those stale flags and new `session.purpose`, even when menu is terminal. `syncAudioForGameplay` plays only when gameplay state is `playing`; normal signed checks did not see it on the new calibrating state.

## Most likely root cause
For the demonstrated transport defect, replacement reuses package ID and bypasses the new-song cleanup, retaining the completed run's start intent across a fresh chart/audio selection. This explains the visible stale transport. It does **not alone prove** the reported audio-only playback; a later browser/media race or UI action may be needed.

## Alternative hypotheses
1. An in-flight audio play/resume or preview command races with reimport: plausible under physical timing, but signed instrumentation recorded no post-completion source.start/media.play in the controlled reproductions.
2. Media lease/camera continues after terminal song: signed controlled Play/Test showed lease idle, CV/video paused; real physical browser remains unobserved.
3. Browser extension/Glitch autoplay: no confirming exception in exported LastPass-only console log, and no basis to blame it.
4. The new authoring conversion freeze causes stale frame presentation: known real signed main-thread 30–42 s reload stall, separately fixed in bounded source, but it does not itself start audio.

## Why previous fixes failed
No audio-only source fix has been attempted. Earlier A selected Reimport QA checked active package hash and chart, not the completed session action flags or post-Reimport audio silence. Test-only completed-song QA did not cover scored Play; that second bounded QA now ran and found the same stale flags but not an audio source start.

## Unknowns and minimal reproduction
The minimal reproducible *transport* anomaly: isolated pinned 5e, finish an actual scored Play or Visual Test, open menu, click selected Reimport, inspect flags/transport at finish. Autoplay itself has no repeatable controlled reproducer after direct/iframe four Test and two Play cases; Derrick's precise physical gesture/timing, Brave page state and whether another start/preview intent was pending are unknown. A real physical session replay or instrumented browser call stack when unsolicited `AudioBufferSourceNode.start` occurs would distinguish these alternatives; do not invent it.

## Proposed verification and recommended fix
Before installing newly persisted content for a completed/stopped *same song*, clear the previous session's `sessionStartRequested`, `activeSessionAction` and stale session generation; preserve the terminal menu and do not start any media. Do not clear an active old run before the replacement is validated, so failed import leaves it usable. Verify signed/source real completed Play and Test Reimport direct+iframe: no active transport or spontaneous source.start through +10 s, new selection loads, explicit Play/Test still starts normally. The separate reported audio-only symptom remains a physical verification gap; avoid claiming this stale-flag fix definitively solves it without reproduction.
