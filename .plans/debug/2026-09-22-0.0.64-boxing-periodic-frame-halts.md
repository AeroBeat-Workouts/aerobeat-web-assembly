# 0.0.64 Boxing periodic frame halts

## Exact Observed Failure

Derrick reports raw 0.0.63 Boxing halts for several frames every few beats on Beat Saber **Wario Ware**, Hard. The Info box also reports `Cannot read properties of undefined (reading 'rotationZDeg')`.

A minimal current-source reproduction proves that every selected uppercut takes the same failing path:

```text
selected state: upercut
validated config state keys: straight, uppercut, hookL, hookR, guard
read: config.states['upercut'].rotationZDeg
error: Cannot read properties of undefined (reading 'rotationZDeg')
```

## Expected Behavior

Boxing render/display work completes every frame for every authored action family. Upcoming uppercuts apply their configured state rotation without throwing. No beat-family cadence produces multi-frame frame-loop aborts or Info errors.

## Execution Path

1. Display loop advances gameplay/content and enters `renderGameplay()`.
2. Boxing computes per-hand state rotations before equipment records are rendered.
3. The next uppercut remains inside `upcomingBeatWindowMs = 500` across many consecutive display frames.
4. `selectGloveState()` returns `upercut` (misspelled).
5. Defaults/schema/YAML use `uppercut`.
6. `computeBoxingStateRotations()` dereferences `.rotationZDeg` on undefined.
7. The outer display-frame catch reports the error; frame work after the throw is skipped.
8. Because the action remains upcoming across a 500 ms window, the exception repeats for several frames. A chart with periodic uppercuts presents this as a halt every few beats.

## Most Likely Root Cause

A cross-module spelling mismatch introduced with 0.0.63 C3:

- selector and its unit expectations: `upercut`;
- validated default/config state tree: `uppercut`.

The exact error text, beat-family timing, and multi-frame duration all follow directly from this mismatch.

## Alternative Hypotheses

1. Renderer/entity allocation or GC: possible secondary performance cost, but does not explain the exact Info error; profile after typo repair.
2. Collision settlement spikes: possible on dense charts, but the proven exception occurs before equipment render completion and persists for the lookahead window.
3. Vignette/aftermath pixel work: lower likelihood; existing target-hardware ABCCBA passed and the regression is specific to Boxing beat cadence.
4. Console/error projection itself adds cost: likely amplifies the stall but is downstream of the typo.

## Why Previous Fixes Failed

Unit tests duplicated the misspelled state list and therefore blessed it. Browser matrices projected uppercut render events directly without exercising `computeBoxingStateRotations()` against the validated config tree. The release performance profile used a synthetic historical workload and did not require an uppercut-dense action mix or assert zero frame-loop errors.

## Minimal Reproduction

Call `selectGloveState()` for an upcoming `family:'uppercut'`, then use its result to index `validateEquipmentConfig(equipmentConfigDefaults).boxing.glove.states` and read `rotationZDeg`. Raw 0.0.63 throws deterministically.

## Proposed Verification

1. Add a closure oracle: every possible selector result must be an own key of validated `boxing.glove.states`.
2. Add integrated render rows for left/right upcoming uppercuts across the lookahead window and assert no Info error, completed frame count, and correct rotation.
3. Profile an uppercut-dense exact Wario Ware Hard fixture on target hardware, comparing pre/post long frames and frame-loop error count.
4. If stalls remain, capture long-task/renderer/GC correlation before any further fix.

## Independent performance diagnosis addendum

The performance child identified a second 0.0.63 Boxing-only regression introduced with C3: `renderGameplay()` calls `computeBoxingStateRotations()`, which calls `boxingUpcomingActions()`, which calls the complete `rendererFrame()` projection solely to read targets; `renderGameplay()` then calls `rendererFrame()` again for the actual render. Flow does one projection per display frame. Each projection rebuilds target, judgement/outcome, aftermath, and hazard structures; the cost and allocation pressure grow with accumulated chart history. A 3,110-input synthetic scale matching the likely BeatSaver map `1BB8` measured roughly 1.195 ms/display for one pass versus 2.292 ms/display for two at 3,000 judgements in Node (directional, not a physical stall proof).

This duplicate projection does not explain the exact Info error, but it is a release-boundary Boxing-only performance defect and plausible GC amplifier. The smallest semantics-preserving repair is to compute one frame per display, pass its `nowMs`/`targets` into glove-state selection, and render that same frame. This also guarantees the glove state and visible targets use one projection snapshot.

Likely exact map match (not yet proven against Derrick's IndexedDB): BeatSaver `1BB8`, `WARIO WARE in BEAT SABER`, Standard Hard, SHA-1 `4ce653b8f9497e259555e7b7126fe2132e19f723`, with 2,602 notes, 294 bombs, and 214 obstacles.

## Recommended Fix

Canonicalize `uppercut` across selector, constants, JSDoc, tests, and serialization assumptions. Make the closure oracle derive expected keys from the validated config rather than maintaining a second typed string list. Compute `rendererFrame()` exactly once per displayed Boxing frame and reuse its target projection for glove-state selection and rendering. Then profile the exact chart before declaring the performance regression closed.

## Post-fix bounded target-hardware A/B

A read-only headed-X11 Chromium run on the RTX 3080 compared exact immutable 0.0.63 commit `b0bad3b` against exact fix commit `f2d02a1`, isolated from the dirty canonical worktree. The workload contained 3,110 events, 2,800 settled judgements, and uppercut-dense upcoming actions at the likely 1BB8 scale.

- exact `rotationZDeg` failures: 60/60 raw frames; 0/60 fixed frames;
- renderer projections/display: 2.0 raw; 1.0 fixed;
- mean renderer+projection CPU: 3.215 ms raw; 2.433 ms fixed (-24.3%);
- p95 CPU: 4.70 ms raw; 3.60 ms fixed (-23.4%);
- in-window heap growth: directionally 22.3% lower fixed;
- long tasks and >33.34 ms frames: zero in both lanes on this desktop;
- projected-target and score snapshot hashes: identical.

Verdict: GO for the two proven P3 fixes (exception elimination and single-frame projection reuse). This test demonstrates less CPU/allocation work and preserved projection/score semantics; it does not claim a full physical-camera reproduction of Derrick's halt. Exact BeatSaver package import plus physical play remains a release retest item. Machine evidence: `.plans/evidence/2026-09-22-0.0.64-boxing-p3-headed-ab.json`.
