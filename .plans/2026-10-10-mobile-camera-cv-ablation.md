## Measurement and phone protocol

- Display **rendered/displayed scene FPS**, not camera FPS or CV FPS, sampled from actual frame timestamps. Show a rolling number and a per-mode timed summary. Label the camera *new-frame rate* separately; display FPS alone cannot prove 30 fresh camera inputs per second.
- Capture per-mode scalar evidence: mode, source revision/build marker, phone/browser, viewport/DPR, selected render scale and actual backing size, camera requested/actual dimensions and frame rate, display FPS and display-interval p50/p95/max, missed-vsync count, camera-new-frame rate, CV submissions/pose outputs, CV runtime and pose-age p50/p95, and mode/setup errors. Avoid serializing raw frames, device IDs, pose coordinates, or screenshots. Provide one tap-to-copy compact JSON report for all completed mode/scale windows, with a download fallback and a visible confirmation/error. No phone SSH, ADB, account, cloud upload, or server-side telemetry endpoint is required. The on-screen summary remains readable without copying. Derrick can paste the report into chat after all three runs; observations about visible stutter, camera lag, and heat are useful alongside the numbers.
- Camera modes require a user gesture and secure origin (`https` or trusted localhost); show a meaningful permission/unsupported-camera error. Do not automatically request camera in Game mode. Stop CV before downgrading to Camera, and stop camera tracks on Game, disconnect, or page exit; prevent stale async mode switches or duplicate workers/streams. Hidden-tab windows are invalid/paused, not averaged into an FPS result.
- Warm up assets and camera/CV before starting each measurement. Then capture comparable **60-second sustained windows** in the order Game → Game + Camera → Game + CV, at fixed scale and physical position. Repeat at another resolution if needed. Record a shorter preview window while iterating but label it non-authoritative. Keep power state/thermal conditions, orientation, lighting, visible-person framing (CV), and background activity as consistent as practical. Avoid using a desktop synthetic-camera run as Moto evidence.
- Interpret each mode separately: Game below 30 means render workload needs attention; Game >=30 but Camera below 30 implicates camera/video composition; Camera >=30 but CV below 30 implicates current CV path; all three >=30 display FPS still does **not** prove 30 pose updates because current CV submissions cap at 15. A Camera pass is headroom evidence, not a proof that any future seven-point engine meets its inference budget.

## Debug record: first independent QA findings (2026-10-10)

**Exact observed failure:** Browser preview passes, but code review found an invalid 60-second run can be recorded if the tab was hidden during warmup or the canvas was resized during measurement. A frozen video can be submitted repeatedly as a fresh `VideoFrame`. These are counterfactual risks, not yet observed failures on the Moto.

**Expected behavior:** Only visible, same-geometry windows with distinct camera frames qualify as valid measurements; a lost camera, permission failure, or CV failure must be visible and absent from completed runs.

**Execution path:** `changeMode` starts the stream/worker; `frame()` warms then records while visible-only invalidation currently handles only `phase === "measuring"`. `ResizeObserver` calls `renderer.resize` without invalidating a window. `createLockedVideoFrameSource` checks `video.readyState`, not a distinct callback frame; `createLockedProductionCvService` submits frames on its timer using a fresh `performance.now()` timestamp.

**Most likely root cause:** The diagnostic copied real production CV admission (valid for gameplay) without adding a diagnostic-only freshness gate, and its mode state machine has no single eligibility check spanning visibility, input freshness, and backing geometry. Evidence: `src/phone-performance.js` visibility handler, resize handler, and CV start, plus `src/production-cv-service.js` source availability/timestamp methods. Native rendering/OS throttling and a slow GPU remain alternative physical explanations; they do not explain this bookkeeping flaw.

**Alternative hypotheses:** Browser `requestVideoFrameCallback` may stop whenever video freezes, so the existing independent camera-new-frame counter itself remains accurate; it does not stop CV from resubmitting a held frame. `getUserMedia` may reject on backgrounding in some browsers, but success while hidden is permitted and cannot be trusted as a general safeguard.

**Why previous fixes failed:** The initial implementation had no targeted hidden-warmup, freeze-frame, or resize-mid-window tests; its passing preview only covered the happy path. The existing 15-FPS CV timer measures inference throughput, not unique-camera-frame throughput.

**Unknowns and minimal reproduction:** Hide the tab during CV warmup and reshow it after the clock elapsed; change backing scale or viewport halfway through a window; hold `requestVideoFrameCallback` while leaving a video ready and observe that CV submissions continue. Tests with fake camera and instrumented callback source distinguish diagnostic-state failure from device/browser throttling. No physical Moto rate is known yet.

**Proposed verification:** Add project-owned browser assertions for hidden warmup, frozen-camera callback, mid-window resize, and CV failure. Require invalid/incomplete windows to stay out of JSON. Verify no production CV/profile modification and regression tests pass after changes.

**Recommended fix:** Keep production CV service untouched. In diagnostic mode, wrap its source with one-use requestVideoFrameCallback eligibility/timestamp and a stall check; invalidate any active window on hidden/geometry/input loss, with explicit visible restart. Record requested and negotiated camera constraints and mode errors. Expand named visual/behavior assertions before full gate and secure staging.

**Debugging record:** Problem: unreliable phone evidence; observed symptom: eligible state not enforced; root cause: independent timers/resize/visibility and CV readiness do not share a measurement-validity boundary; evidence: source and QA review above; failed approaches: happy-path preview alone; corrective action: eligibility gate and targeted tests; verification test: hidden/frozen/resized windows fail while stable windows pass; related files: `src/phone-performance.js`, `src/production-cv-service.js`, browser test; remaining uncertainty: Moto hardware behavior until Derrick runs 60-second windows.

## Debug record: selector retry bypass (2026-10-10)

**Exact observed failure:** Independent QA found that changing render resolution after an invalid Camera/CV window calls `beginWindow()` without acquiring a camera stream or Worker. During an active window, the selector marks a run invalid but immediately begins another one without an explicit retry. These are source-confirmed paths; the Moto has not yet exercised them.

**Expected behavior:** Every new Camera/CV measurement must have a live stream (and Worker for CV), and an invalid window must require a deliberate mode-button retry. Changing scale selects the next configuration, not a silent recovery from invalid state.

**Execution path:** The `aero-select-change` listener in `src/phone-performance.js` calls `invalidate(...,false)` during measuring/warmup, then changes `renderScale` and calls `beginWindow()` when phase is `invalid` or `done`. `invalidate(...,true)` previously stopped camera/CV on hidden/stall/error; the selector does not call `changeMode()` to reacquire them. `beginWindow()` resets the time/configuration but never acquires resources.

**Most likely root cause:** Selector handling conflates configuring resolution with restarting a mode, bypassing `changeMode()`'s resource ownership and the manual-retry boundary. The branch condition itself proves the path; QA independently found it. It is not an issue with the production CV timer or camera permission API.

**Alternative hypotheses:** A still-running stream after a mid-window scale change may allow technically valid measurement; nevertheless the plan explicitly requires an invalid window to wait for a user-triggered restart. After hidden/stalled Camera/CV, the resources are stopped, so the bypass is unambiguously wrong. A CSS-only resize could be harmless, but the code changes actual canvas backing and must reset comparison.

**Why earlier fixes failed:** The visibility/geometry guards and fresh-frame gate focused on rejecting bad results; the browser gate checked invalidation itself but did not change scale *after* invalidation. The selector branch remained independent of mode acquisition.

**Unknowns/minimal reproduction:** In the 4-second fake-camera preview, enter Camera/CV, hide and show the tab or force a stall, select Low, then wait: the old path shows warmup/measuring without a new `getUserMedia` or Worker. Also change quality halfway through a visible run and inspect whether a second run starts without a mode click. The exact phone UI timing remains unmeasured.

**Proposed verification:** Add a browser assertion that invalid + quality stays invalid with no completed run or new camera request; a deliberate mode click starts a fresh comparable run. Change quality during measurement and verify it invalidates without automatically saving or restarting; check CV cleanup and source revision/protocol. Counterfactually remove the production fix in an isolated worktree and require this assertion to fail.

**Recommended fix:** Let the selector resize immediately but leave invalid/warmup/measuring windows invalid and display a mode-button retry prompt.
