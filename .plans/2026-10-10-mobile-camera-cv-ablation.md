## Goal

Give Derrick one phone-accessible, self-contained diagnostic using AeroBeat's existing deterministic dense PlayCanvas gameplay workload to compare **Game**, **Game + Camera**, and **Game + CV** at the same render resolution. Derrick confirmed the deterministic test scene for this experiment. Establish whether the phone can render that workload at 30 FPS with the camera active before investing in a custom pose model. This is a diagnostic, not a production CV/scoring change or a claim that 30-FPS pose output is already feasible.

## Proposed experience

Create a separate, clearly labeled **Phone Performance Test** page in the assembly repo, without replacing or altering the normal `<aero-game>` route or an immutable raw release. Use the exact dense Flow PlayCanvas scene/workload above, with the same camera-facing perspective and continuous moving beats. Keep scene, timeline rate, target density, CSS canvas size, environment, and renderer settings identical across modes; reset the test timeline and measurement window on mode change. The test does not require BeatSaver download, music, calibration, scoring, or player movements; these would make the three runs harder to compare. State this scope visibly so the result is not mislabeled a complete scored-run benchmark.

- **Game:** Scene and moving beats only. No webcam request, live video playback, transferable frames, Worker, or MediaPipe initialization. Verify zero camera tracks and zero CV submissions.
- **Game + Camera:** Exactly the same scene, plus live front-camera playback/compositing through the normal video presentation path at the game's normal camera constraints. No MediaPipe initialization, no pose inference, no CV Worker, no VideoFrame capture/transfer. Count actual *new* camera frames via `requestVideoFrameCallback`, independently from display frames; show camera dimensions and negotiated track FPS. This isolates camera acquisition/decode/video presentation but does not claim to measure capture/transfer overhead.
- **Game + CV:** Same scene and camera presentation plus the current locked MediaPipe Lite CPU-WASM Worker/transferable-VideoFrame route, measured at its **existing 15-FPS submission ceiling**. Consume its latest pose for diagnostics but do not gate scene animation on calibration, pose presence, or tracking loss. Report measured pose-output FPS, inference p50/p95 and pose age alongside display FPS. If lack of a visible person produces no landmarks, inference/camera activity must still be truthfully reported, not simulated. This compares current production CV cost; it is not a 30-pose-FPS claim.

The three buttons are mutually exclusive modes, not simultaneous independent toggles. Use touch-sized `aero-button` controls with a clear selected state. Provide an `aero-*` FPS HUD at the **top** with a dark/contrasting background, legible over the moving scene and camera, and a labeled native-accessible readout. Prefer the existing `aero-status-panel` HUD with a dark, opaque `::part(panel)` treatment and contrasting text; add a dedicated `aero-performance-hud` in `aerobeat-web-ui` only if this existing component cannot present readable bounded scalar FPS cleanly. Assembly remains responsible for timing and mode lifecycle. Add a render-resolution `aero-select` with the same labels/values and `renderScale` implementation as the current gameplay-menu dropdown; show the selected scale and effective canvas backing dimensions. Keep it visible on phone portrait and landscape. No duplicate scaling implementation.

## Measurement and phone protocol

- Display **rendered/displayed scene FPS**, not camera FPS or CV FPS, sampled from actual frame timestamps. Show a rolling number and a per-mode timed summary. Label the camera *new-frame rate* separately; display FPS alone cannot prove 30 fresh camera inputs per second.
- Capture per-mode scalar evidence: mode, source revision/build marker, phone/browser, viewport/DPR, selected render scale and actual backing size, camera requested/actual dimensions and frame rate, display FPS and display-interval p50/p95/max, missed-vsync count, camera-new-frame rate, CV submissions/pose outputs, CV runtime and pose-age p50/p95, and mode/setup errors. Avoid serializing raw frames, device IDs, pose coordinates, or screenshots. Provide one tap-to-copy compact JSON report for all completed mode/scale windows, with a download fallback and a visible confirmation/error. No phone SSH, ADB, account, cloud upload, or server-side telemetry endpoint is required. The on-screen summary remains readable without copying. Derrick can paste the report into chat after all three runs; observations about visible stutter, camera lag, and heat are useful alongside the numbers.
- Camera modes require a user gesture and secure origin (`https` or trusted localhost); show a meaningful permission/unsupported-camera error. Do not automatically request camera in Game mode. Stop CV before downgrading to Camera, and stop camera tracks on Game, disconnect, or page exit; prevent stale async mode switches or duplicate workers/streams. Hidden-tab windows are invalid/paused, not averaged into an FPS result.
- Warm up assets and camera/CV before starting each measurement. Then capture comparable **60-second sustained windows** in the order Game → Game + Camera → Game + CV, at fixed scale and physical position. Repeat at another resolution if needed. Record a shorter preview window while iterating but label it non-authoritative. Keep power state/thermal conditions, orientation, lighting, visible-person framing (CV), and background activity as consistent as practical. Avoid using a desktop synthetic-camera run as Moto evidence.
- Interpret each mode separately: Game below 30 means render workload needs attention; Game >=30 but Camera below 30 implicates camera/video composition; Camera >=30 but CV below 30 implicates current CV path; all three >=30 display FPS still does **not** prove 30 pose updates because current CV submissions cap at 15. A Camera pass is headroom evidence, not a proof that any future seven-point engine meets its inference budget.

## Decision gates for discussion

- **Scene parity (confirmed by Derrick):** use the existing 6,000-event ABCCBA synthetic Flow renderer workload as the common test, rather than requiring a downloaded song or full scoring/calibration pipeline.
