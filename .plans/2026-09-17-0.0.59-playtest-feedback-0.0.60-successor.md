### F2 — boxing corpse spawns right of the hit spot (ROOT CAUSE CONFIRMED)
- **Two different X conventions for the same physical columns:**
  - **Wrist/judge space:** `measuredColliderSample` (flow-collider-collision.js:~75) maps the calibrated body-grid anchor to `sx = 4·x_norm − 0.5` → column centers at **x = 0, 1, 2, 3**. The judge plane uses the same convention: `targetCenterForPlacement(placement) = {x: placement % 4, …}` (flow-collider-collision.js:78) and `boxingColliderTargetCenter` (boxing-collider-collision.js:121-123).
  - **Presentation space:** the visible note icon renders at `worldPositionForCell(cell)` → `x = columnX[col] ∈ {−1.5, −0.5, 0.5, 1.5}` (gameplay-scene-model.js:44,109-113); the boxing_collider `targetPositions` branch keeps that X and only swaps Y for the reach row (:392-404); at hit, `iconRenderPosition` pins `z = 0` (:374-376). Collider overlays anchor at the same icon position (:822-833) — the note's disappearance point is (columnX[col], reachRowY, 0).
- **Consequence:** for EVERY cell the corpse (B15: `punchCellToRenderedPositionZ0` → x = `cell % 4`) spawns **exactly +1.5 WU to the right** of where the visible note disappears. Computed screen space (camera {0.05,1,5}, vfov 48°, 844×390 canvas → 87.6 px/WU at z=0): **constant +131.4 px right for all 12 cells** (≈ +303 px on a 900 px-tall viewport); Δy = Δz = 0 (Y and Z already match). This is Derrick's "a few units to the right" — 1.5 world units.
- **B15's premise was wrong — and B15 regressed X while fixing Y.** Pre-B15, `gridCellToWorldZ0` already gave the note-matching X (columnX) and only the top/bottom-row Y jumped (old full-grid rowY 2/1/0 vs reach-row Y, ~0.75 WU). B15 moved boxing to `punchCellToRenderedPositionZ0`: Y fixed, X changed from columnX to `cell % 4` on the false premise that "the renderer renders the punch icon at x = placement % 4" (that is the JUDGE plane, not the icon). B15's unit tests compared corpse-vs-judge-plane (identical by construction) and pinned the WRONG values (validate-gameplay-frame-effects.js B15 block).
- **The canvas-freeze artifact (bead `iy23`) is explained — it was never a freeze:** the B15 real-pixel oracle built events with `type`/`spatialTarget` at TOP LEVEL and NO `authoredBeat` → `projectSessionTargets` (reads `authoredBeat.type`, session-render-projection.js:100) fell back to "note" → punches projected as FLOW targets with `cell: null` → the renderer's boxing_collider branch hit the LANE fallback (x=−0.9 for every left-hand punch) → pixel-identical frames between punches. Additionally the oracle's expected note position used the same false `cell % 4` identity (self-referential), had one fixed baseline mixing note/feedback pixels into the diff, and flipped Y twice. Re-run this session: runs to completion, all renders advance, Δ≈48.4 px (a mixed-centroid artifact, not the true 131 px).
- **Fix (W2):** in `punchCellToRenderedPositionZ0` (gameplay-frame-effects.js:145-156) replace `const x = cell % 4` with `const x = gameplayWorldGrid.columnX[cell % 4]` (import from `@aerobeat/web-renderer` — dependency already exists, exported from the package root); keep Y (`boxingColliderRowY`) and z=0 (both already correct); rewrite the B15 comments (renderer world = judge x − 1.5). ### F4 — tracking loss pauses the song (ROOT CAUSE MAPPED; DESIGN REVISED PER DERRICK)
- **Current chain:** loss detection in `body-grid-service.js` (3 loss anchors nose/left/right-wrist, conf ≥ 0.5; three trigger paths: 3 consecutive low-conf frames + 750 ms window; silent gap ≥ 750 ms; no-frame `advanceTime` ticks at ≥15 Hz) → `triggerTrackingPause` → `invalidateCalibration("tracking_lost")`: `readiness="paused_tracking"`, `freshCalibrationRequired=true`, `latestEvidence=null`, `resetMeasuredHistories()` (anchors cleared → markers vanish). Coordinator `enforceSafety` → `state="paused_tracking"` → audio pause + `seek`; resume demands `freshCalibrationRequired` cleared — partial auto-recovery (300 ms hold) usually fails → **full T-pose** (2000 ms).
- **Derrick-approved spec (0.0.60) — REVISED from the first draft:**
  1. **No pause, no T-pose** on mid-run tracking loss: session stays `playing`, audio keeps playing, next good frame resumes following — no gesture.
  2. **SCORING CONTINUES during the freeze (revised):** the brief losses happen mid-swing, so disabling collisions would miss notes he actually hit. **Positive AND negative events still fire while tracking is lost** — the last-known (frozen) wrist positions remain SCORING-ELIGIBLE: a note whose target is at the frozen fist position (the punch he threw when tracking dropped) HITS; a note that passes without contact MISSES as usual. The ghost-hit trade-off (a hit can register from a frozen position) is **explicitly accepted** — it is the intended "notes you thought you hit still count" behavior.
  3. **Markers (revised):** frozen at last position AND **dimmed per-anchor** — the specific hand/nose marker whose tracking dropped goes dim while lost and restores full brightness when its landmarks return (Derrick plays without the grid, so the per-marker dim is the user-visible signal; the grid's existing `tracking_lost` dim stays as a debug affordance).
  4. Initial T-pose calibration and source-change (camera) recalibration UNCHANGED.
- **Design direction (W4 implementation lane):**
  - **contracts:** `anchorsFrozen` on the tracking safety snapshot + per-anchor degraded state (which wrist/nose is currently lost, for the per-marker dim); a frozen-evidence shape (held position, per-tick evaluation identity, distinct from `provenance:"measured"` so the measured-frame monotonicity contract stays intact).
  - **input (`body-grid-service.js`):** calibrated + loss → `anchorsFrozen=true`; keep `latestAnchors` (markers freeze) AND keep publishing the held evidence (position held, per-tick identity) instead of nulling it; track per-anchor degraded flags from the low-confidence conditions; passing sample clears freeze + restores on the very next good frame; uncalibrated + source-change keep the old full-pause+T-pose path.
  - **gameplay (`session-coordinator.js`):** the collider paths accept frozen evidence with the 150 ms freshness gate EXEMPTED for frozen frames (the monotonic-frameId gate must not swallow a held frame — per-tick identity so new events are re-evaluated against the held position); `judgedIds` remains the double-hit guard (an event can never hit twice across frozen ticks); swept contacts stay impossible from one held frame (point-contact path carries frozen hits); miss finalization unchanged (negative events fire).
  - **assembly (`index.js`):** `gameplayCursorRecords` emits frozen anchors (instead of dropping them) with per-anchor `dimmed` for the lost ones; telemetry.
  - **renderer:** dim the dimmed cursors (material/alpha on the existing cursor primitive).
- **Tests (extend, deterministic, no camera):** `validate-body-grid-service.js` — freeze enter/exit, hysteresis, anchor retention, frozen evidence published, per-anchor degraded flags, resume without T-pose, uncalibrated still pauses, source-change unchanged. `validate-gameplay-session.js` — **frozen on-target note → HIT** (the new core case), off-target → MISS, no double-hit across frozen ticks (judgedIds), state stays `playing`, audio/lease paths unaffected.
- **Closes bead `tm4m`.**

### F1 — flow corpse still gray (B13 re-open; ROOT CAUSE CONFIRMED — two independent causes)
- **(1) The corpse fill is the NOTE'S REAL FILL, 0.92-lerped to grayscale — and this song's note fill is a PALE BeatSaver palette color.** Real flow events always carry `appearanceColor = palette.left|right` (content-runtime.js:465; flow beats always have `hand` + boolean `requiresDirection`, converter.js:325 / package-content.js:423-429). The assembly threads it onto the aftermath entry (B11b: gameplay-frame-effects.js:398/435-436) — so B13's role-from-hand is only the FALLBACK (used when `appearanceColor` is ABSENT); in the real pipeline it is always present and the fallback never fires. The renderer desaturates the real fill: `aftermathCorpsePartColor` note_fill branch (renderer-facade.js:368-372) = 0.92 lerp of `appearanceColor ?? roleColor` toward luma grayscale (`AFTERMATH_CORPSE_DESATURATION=0.92`, gameplay-scene-model.js:89). Computed: pale saber color `#A8C8E8` → corpse (193,196,198), b−r≈5, luma≈196 — **exactly the observed pale gray/lavender ~180-200**.
- **(2) The 0.92 desat is too strong to ever read "clearly colored by hand":** even the SATURATED default `#2693FF` collapses to (124,133,141) = blue-GRAY (spread 17); `#39C96B` → (155,167,159) (spread 12).
- **Why the B13 oracle passed:** its fixtures only tested (a) no-appearanceColor (saturated role fallback) and (b) `appearanceColor:#2693FF` (the saturated default) — never a pale/near-white fill like the real song's. And its assertions REQUIRED a desaturated result (`bMinusR>12`, `55<luma<160`, `meanSat<40` — "strongly desaturated, tint not saturated" = literally asserting a gray-ish corpse as PASS). The real pale fill (luma ~190-220, meanSat ~5) is outside those bands — a faithful fixture would have FAILED. Same "code test ≠ e2e proof" failure mode, root: fixture shape + assertion polarity both matched the wrong path.
- **Why boxing reads "colored" (OPEN — W1 probe adjudicates):** the corpse color path is SYMMETRIC — flow and punch entries both carry the same shared-palette `appearanceColor` and render through the same `aftermathCorpsePartColor` (flow via the slice-variant path, punch via the whole path). The code does NOT structurally make boxing bluer. Best explanation: perception — a boxing punch is one larger solid arrow sitting next to its saturated live note + hit flash, while a flow hit is two small falling halves; and/or the boxing session hit the more-saturated palette side. **W1 step 0: runtime probe** — dump *Incomplete* Normal's `effectiveNotePalette` (left/right hex) from the served app's content runtime + read one real flow-vs-boxing corpse fill side by side in real pixels.
- **Candidate fix (starting point for the sweep loop, renderer):**
  - `aftermathCorpsePartColor` note_fill branch (renderer-facade.js:368-372): if the note's real fill is near-achromatic (channel spread < threshold, start ≈0.18 sRGB), substitute the saturated HAND color (`roleColor(role)` — B13 already resolves flow/punch roles to left/right) as the desat source before the lerp. Saturated fills keep their own tint (B11b intent preserved); pale/gray fills become the hand color.
  - Companion: lower `AFTERMATH_CORPSE_DESATURATION` from 0.92 → ~0.55 (UNCALIBRATED start) so surviving color reads as clear blue/green instead of a gray wash. At 0.55: `#2693FF`→(98,147,195) clear blue, `#39C96B`→(93,157,115) clear green.
  - Assembly unchanged (B13 threading is correct). Optional deeper fix NOTED, not this cycle: `colorTokenToRgba` returns sRGB but it is set as LINEAR diffuse (GPU gamma lightens mid-tones further) — true color-space fix = linearize before the lerp (broader change).
- **SECOND + THIRD ROOT CAUSES (found while building the sweep harness, 2026-09-17):**
- **(2) Slice-variant material cache key bug (renderer, latent since 0.0.52 bffc340):** `sliceVariantMaterial` keyed the cache with the meshInstance OBJECT interpolated into a string ("[object Object]"), so ALL three material parts of a flow slice half collided on one cache entry — the first part's clone won and the last part's color painted the entire half FLAT. Flow (slice) corpses therefore never rendered the white outline / charcoal / tint structure — a single flat color, in every build since 0.0.52. Punch (whole) corpses use a different path and were unaffected (matches the playtest: flow flat, boxing structured). B11b's per-part contrast logic was correct at function level but invisible in pixels; every prior pixel oracle either measured the flat fill or (as found below) the wrong pixels entirely. **Fixed:** unique per-record `materialUid` in the key (renderer 59f91ee).
- **(3) Aftermath-to-aftermath pool contamination (renderer):** a pooled aftermath entity that rendered a SLICE half in a previous frame kept its clip-blocked variant material; a subsequent WHOLE corpse on the same slot rendered clipped (slice notch on a punch orb). Live-icon reuse was already protected (restoreSliceMaterials in applyAssetAppearance) but aftermath-to-aftermath reuse was not. **Fixed:** whole aftermath path restores plain pooled materials first (renderer f5a08fd). (Cannot manifest in a single-mode playtest session — flow always slice, boxing always whole — but breaks any mixed-mode frame and the sweep harness.)
- **Sweep harness crop bug (harness, fixed + guarded):** the first contact-sheet run cropped the canvas AFTER `frame()` had re-rendered the baseline — stats (from captured pixels) were correct but every crop showed the scene WITHOUT the corpse (Derrick caught it: "all show the same bug, no white outline"). Fixed: crop before re-render + a glyph-presence guard that fails the run if a crop doesn't contain the glyph. Lesson: pixel evidence must be visually verified, not just numerically asserted.
- **Evidence:** `scripts/sweep-corpse-colors.js` (on-demand e2e; BEFORE_PIN for true pre-fix comparison; flow-arrow/flow-orb/punch-orb kinds; dual-phase sheet + measured table). Current state: `.plans/evidence/2026-09-17-v3-corpse-sweep-combined.png` — BEFORE = a517aa2 (flat, washed), AFTER = desat 0.55 + chroma 0.35 + both slice fixes (white outline + colored fill on every glyph, arrows included). **Awaiting Derrick's sign-off on the look/constants.**

### F3 — straight punches hittable by either wrist (ROOT CAUSE CONFIRMED + REPRODUCED)
- **Root cause (reproduced end-to-end on current code):** straights are **overlap-only** and their inflated footprint **permanently covers the player's raised guard fists**:
  - `boxingAuthoredDirection()` returns `undefined` for straights (boxing-collider-collision.js:146-151); `matchesBoxingAuthoredDirection()` short-circuits to `true` for `direction === undefined` (:284-289), applied at session-coordinator.js:1000. Hooks/uppercuts require ≥0.05 WU directed travel in a ±45° cone (flow-collider-collision.js:53,149-158) — a stationary fist can never satisfy that; it trivially satisfies overlap.
  - Contact = pure position+timing overlap, half-extent `0.375 + colliderRadius(0.12) = 0.495` WU, against `boxingColliderTargetCenter` (judge space x = 0..3).
  - Straight targets live in the CENTER columns — converter.js:307: `column = hand==="left" ? 1 : 2`. X slabs: straight_left [0.505,1.495], straight_right [1.505,2.495]; row-Y slabs (default 0.25 reach) cover the whole chest/shoulder band.
  - The canonical raised-fist guard pose (repo's own guard fixture → judge-world (1.26,1.06)/(1.74,1.06)) returns `pointContactsBoxingTarget = true` for **both hands on every straight cell in all three rows** (empirically executed this session).
  - **Repro (Derrick's report verbatim):** right fist STATIC at guard (1.74,1.06) while the left hand jabs → `straight_right` judges **HIT**. The credited wrist is the event's own hand — it just wasn't punching; the idle raised fist absorbed the hit. During fast alternation the orb on the idle hand's side pops at the moment the other arm swings — reads as "the wrong wrist hit it."
  - The hole is codified in tests: validate-boxing-collider-scoring.js:492-500 ("straight counts on pure overlap without any hold evidence"); judge comment "straight 100ms hold semantics do not apply" (session-coordinator.js:962). The legacy rulesets DO consume the per-hand straight hold (semantic-track :1562-1569, spatial-grid :1608-1613); the collider ruleset dropped it.
- **Ruled out (with evidence):** wrist-anchor mirroring/inversion (anatomical MediaPipe names 15/16 preserved; single (1−x) flip; CSS-only preview mirror); `measuredColliderSample` substitution (exact anchor-name lookup, no fallback); wrong-side rendering (side mapping consistent; colors follow the event hand — matches Derrick's "colored correctly"); hand-less/"any" straight events (converter always emits `${family}_${hand}`, converter.js:209/307); chord cross-attribution (strict per-hand filter); `any_punch`/`cross_body` (no judge-side consumer anywhere — content markers only, off by default for imports).
- **Derrick decision (0.0.60): KEEP overlap-only — do NOT reintroduce the gesture qualifier.** Rationale (Derrick): collision-only straights work well in practice because the athlete's arms rest below the shoulders/beats, so a real straight punch moves the wrist *up into* the beat. His physical repro (moving the left wrist into the right lane and seeing a count) is exactly the idle-own-hand mechanism above — the judge is hand-strict, so it was his RIGHT hand in the box that counted. The fix is reduced to a **proof, not a code change**:
  - **No judge code change.** The straight-qualification gate is DROPPED from scope (the full design is preserved in this plan's W0 section / subagent report as the future lever).
  - **W3 becomes a deterministic scoring-path harness** (no camera; the repo's coordinator-harness pattern, extending `validate-boxing-collider-scoring.js`) proving **the opposite hand cannot affect the opposite hand's beats** — Derrick's requested check: (a) left wrist physically inside the right-lane box (his crossing scenario) with the right wrist far away → `straight_right` = **MISS**; (b) symmetric for `straight_left`; (c) both hands crossing simultaneously → each beat judged only by its own hand. These pass on current code (hand-strictness verified in W0) and serve as the permanent regression guard.
  - **Documented nuance (recorded for the next playtest):** in code, a left wrist physically in the right lane can NEVER credit `straight_right` (the judge reads only the right-wrist sample — W0 repro C/D proved it). The count Derrick experienced therefore came from his **right hand being inside the box** — raised guard fists sit inside every straight box (W0 empirical). That residual (idle own-hand fist absorbing a hit) is inherent to overlap-only and is now **accepted behavior** per Derrick's decision. If "wrong-hand" counts keep appearing in playtest, this is the mechanism — and the straight qualification is the documented lever to pull later if he changes his mind.
