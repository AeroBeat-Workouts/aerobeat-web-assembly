## Why and what remains fixed

Signed old private GPU (`source=76bfd8b25d49426e5962629c5c9caae510577582`, sidecar `ea00d5dae12c96a22a9d010bc5f88df6cc4c5a87c32a58323545963d2f5c2c39`) produced a valid real 60s WebGL Worker report: 7.867 fresh poses/s, 74.3/84.5ms inference p50/p95, 29.867 distinct camera presentations/s, 425/896 busy drops and 272/472 marker-valid frames. The signed CPU control produced 8.333 poses/s, 70.4/81.4ms inference and 396/896 busy drops. The current experiment service polls on a fixed `setInterval(Math.ceil(1000/15))` (67ms), so an inference longer than the next tick often causes a busy drop and another wait. The official demo screenshot shows Lite/GPU/one pose, `.5/.5/.5` thresholds and ~68–71ms **per-inference** metric, not sustained pose FPS. This experiment changes **only scheduling policy**, NOT vendor/model (Lite float16, Tasks Vision1.0.1), detection/presence/tracking thresholds (`.4/.5/.3`), 640×480/30 camera request, mirrored VideoFrame, 15/s ceiling, single-flight invariant, native calibration/markers, 3s+60s window, fallback semantics or production. It cannot perfectly match Google's other runtime, confidence, camera and UI behavior. The goal is to isolate whether fixed-tick busy drops caused part of the observed ~8/s despite ~74ms inference.

## Presentation-ID debugging record before correction

**Exact observed failure (pre-build draft):** service `estimateAfterResult` checks `source.isFrameAvailable()` but does **not** read the paced page's `source.getPresentedFrameId()`. Its first draft claimed media freshness from `getTimestampMs()`, which in the real camera source returns `performance.now()` on every read; a later draft removed that false claim but still accepts a ready video element even when its presentation ID is frozen. This is static code evidence, **not** a served-phone measurement or failing browser assertion. **Expected invariant:** only a strictly advancing `requestVideoFrameCallback(metadata.presentedFrames)` ID may admit a new paced transfer; while camera presentation freezes, time may advance but accepted pose count may not. **Execution path:** `cameraTick` in GPU page records metadata.presentedFrames and exposes `getPresentedFrameId` on after-result source → `normalizeSource` passes source through → `estimateAfterResult` polls `isFrameAvailable` and then `runEstimate`; because service ignores `getPresentedFrameId`, a busy but ready video element can be re-wrapped in VideoFrame and counted anew. **Leading root cause:** admission logic used the read-time clock/readyState as if they were a new video presentation, then discarded the invalid clock check without replacing it with the already-supplied ID. Evidence: original `createLockedVideoFrameSource.getTimestampMs=performance.now`, real page getter exists, service source lacks getter use; first deterministic unit supplied changing clock only. **Alternatives:** a camera track stopping normally causes page `camera_lost` (does not prove all ready-element stalls); natural camera30fps with >67ms Worker calls usually advances (supports lower observed frequency in current run but does not enforce invariant or cover stalls). **Previous fixes:** timestamp comparison falsely treated clock as identity; removing it fixes false documentation, not duplicate admission. **Unknowns:** actual stalled camera/browser rVFC behavior and whether every target phone exposes metadata.presentedFrames; test true fixture and fail-closed unsupported branch, then real browser positive Worker source/ID readback. **Minimal repro:** source stays `isFrameAvailable=true`, `getTimestampMs()` advances each retry, `getPresentedFrameId()` remains 1, adapter resolves quickly; without the gate, a second pose submits for the same presentation. **Verification before code change:** deterministic unit with independent frozen ID asserts no second submit across >67ms and resumed submit after ID increments; run same tests in disposable mutation removing only service ID check to demonstrate bug-specific failure. **Recommended fix:** require callable getter only for after-result, retry bounded while initially absent/unchanged, fail closed on invalid/regressing ID, store last ID only after accepted submission, and ensure `nextPoseFrame/submitFrame` cannot bypass. Keep fixed-tick default and production untouched; cover stop/restart/cancellation and transferable closure in unit plus actual served real Worker QA.
