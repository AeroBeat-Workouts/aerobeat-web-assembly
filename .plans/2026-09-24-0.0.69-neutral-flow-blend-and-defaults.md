## Continuous-motion cadence diagnosis

### Exact observed failure

The independent source auditor reproduced normal center→right-edge motion over one second and found different final shared hit-bearing quaternions at 30/60/120 Hz: 30/60 differ by `0.45929°`, 60/120 by `0.22366°`, and 30/120 by `0.68295°`. The parent independently reproduced the exact quaternion values. The existing cadence oracle passes only because it holds one unchanged endpoint between evaluations.

### Expected behavior

At the same finite hand position and configuration, the approved spatial field must resolve the same orientation regardless of render/evaluation cadence. The square-radius smoothstep field itself is stateless; final renderer/gameplay pose parity must not inherit sampling-rate-dependent lag.

### Execution path

A wrist anchor enters `computeFlowQuaternionTargets()` → `createSquareRadialSaberTargetTracker().tick()` → `squareRadialSaberTarget()` computes the correct stateless target → tracker compares that continuously changing target with its prior endpoint → every frame restarts a 100 ms fixed-endpoint transition from the partially evaluated prior transition → `gameplayEquipmentRecords()` composes the resulting lagged target with the per-hand base → the same frozen but cadence-dependent pose is sent to gameplay collision and renderer.

### Most likely root cause

The tracker correctly implements fixed-endpoint retargeting for discrete step changes, but treats every sample of normal continuous position motion as a new discrete step. Because each frame restarts the interpolation, the number and timing of samples change accumulated lag. This is confirmed by the exact 30/60/120 reproduction and by the unchanged-target test's inability to exercise the branch.

### Alternative hypotheses

1. Quaternion shortest-path instability — contradicted: the stateless spatial target and perimeter oracle are continuous and shortest-path tests pass.
2. Floating-point drift — contradicted: the divergence is monotonic with sample cadence and roughly tenths of a degree, far above numerical roundoff.
3. Renderer/gameplay disagreement — contradicted: both consume the same frozen pose; the defect is shared upstream orientation.

### Why previous fixes failed

The v4 change fixed center history/bootstrap and spatial continuity, but retained the predecessor's temporal tracker. The existing 30/60/120 test assumed a fixed target after one retarget, proving only discrete-step interpolation, not continuous moving-target parity.

### Unknowns

No unknown remains about the causal chain. The product decision is whether Flow should retain sample-dependent temporal lag or prioritize the approved position-defined field. The plan already requires cadence-independent spatial response, so temporal lag cannot remain on ordinary wrist motion.

### Minimal reproduction

Start a fresh tracker at center at `t=0`; linearly sample `x=.5→1`, `y=.5` for one second with the configured linear 100 ms duration at 30, 60, and 120 Hz; compare the final quaternions. Holding `x=1` after one retarget does not reproduce.

### Proposed verification

Add a dense moving-path oracle that evaluates identical center→edge and center→corner positions at shared wall-clock checkpoints under 30/60/120 sampling and requires quaternion equality. Retain exact center, perimeter, shortest-path, and off-grid tests.

### Recommended fix

Make Flow's approved position-defined spatial quaternion authoritative on every tick rather than re-easing each continuously moving sample. Keep the tracker only as a resettable API boundary returning the stateless target and diagnostics; remove unused temporal state/easing from this Flow path. This yields exact cadence parity and preserves the latest config fields/identity without changing Boxing easing. Update the stale v3 comment and test a continuously moving target. Re-run focused field, panel, full unit/browser, scoring, and shared-pose gates.
