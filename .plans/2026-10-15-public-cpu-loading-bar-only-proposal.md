## What is already proved — and what is not

The unpublished signed candidate (`.tmp/friend-game-cpu-stream-candidate-3bdb5e5`, manifest SHA-256 `2afeb4d0383e3830969f034c7b3b9f1bf37223560b78b21030b32c937cf79066`) displays only **decoded pose-model download bytes** over the pinned 5,777,746-byte model. Its project-owned browser tests run in the normal `test:browser` command: real camera/Worker, direct and cross-origin iframe at 390×844, model 25/50/75%, a visible queued Test beside the true Play bar, an indeterminate pre-byte tracker state, and ordered eventual audio-only Test. The default six-second and explicit 35-second delayed-WASM holds passed; old signed public source fails the same 25% visual assertion. Corrupt, truncated, and disconnected model paths fail closed. Neither percent nor CV progress `verified:true` alone proves checksum completion or overall startup completion; a 100% model-download label is not a tracker-ready claim.

**Not release evidence:** the streaming candidate also overlaps model and WASM requests and sometimes produces a same-Worker-model-request `net::ERR_ABORTED,canceled:true` even when the original signed server finishes and the Worker later verifies bytes. The strict same-request comparator fails, including a bounded alternate chunked transport. One clean local timing pair is not reliable speed or phone evidence. Removing a speed claim does **not** excuse an unexplained browser model-request failure. The normal `npm run test:browser` suite also exits nonzero at the historical direct 390×844 DPR3 renderer cadence checks, before the signed progress suffix. A valid pre-stream source/dependency diagnostic fails the same strict audio timeline step as current; this shows pre-existing susceptibility but does not prove the threshold stale or that the candidate cannot regress. Nothing was published; no test threshold or provenance guard was relaxed.

## Proposed implementation after plan approval

1. **Separate download progress from the speed experiment.** On the *public CPU game only*, avoid deliberately overlapping model and WASM GETs. A **model-first buffer** is the only previously tested non-overlapping experiment; the desired WASM-first order is **not yet proved possible** using the pinned public API. Do not treat `FilesetResolver.forVisionTasks()` returning URLs as proof that the WASM binary was fetched. First instrument exact Worker-target model/WASM GET starts/finishes and verify with Tasks Vision 1.0.1 whether an isolated non-overlapping path is supported **without a duplicate GET**. The likely bounded approach is: receive actual **decoded** model bytes from one GET, report true received/pinned-model-length progress, verify exact length and SHA-256, then pass a complete `Uint8Array` through public `modelAssetBuffer` during task construction. This may load model **before** WASM, unlike the frozen game; call out that timing/order difference, memory/copy overhead, and any changed startup time without claiming a speed gain. Keep the public WASM resolver paths, not binary injection. The opt-in streaming-reader candidate is a visual prototype, not safe to publish solely by dropping a speed claim. Compare reader/buffer modes with identical signed identity/Brotli model/WASM bytes, Worker-target same-request request lifecycle, EOF/SHA/loaded/pose, and corruption/disconnect outcomes. **STOP and return options** if pinned MediaPipe cannot construct a usable pose tracker from the complete verified buffer with one model/WASM GET each, if any unexplained browser `ERR_ABORTED` persists, or if the supported non-overlapping path is infeasible; do not fabricate WASM-first or relax the gate.
2. **Keep the honest foreground contract.** Show visible indeterminate preparation before any model bytes and after the model transfer until the tracker really initializes. While bytes arrive, show only a labeled “Pose model download: N%” computed from decoded bytes divided by the independently pinned decoded total; never use compressed HTTP `Content-Length`, synthesize an overall percent, mark SHA/pose ready from the progress event, or expose private CV details. Keep the 390×844 Play/Test buttons usable and show queued Test beside the Play bar. On cancel, disconnect, superseding intent, corruption, or network failure, clear stale progress, report an actionable error, and never send a false `loaded`. Preserve scoring, calibration, camera, private CV/GPU modes, and all existing routes.
3. **Prove the production boundary, not a nice-looking screenshot.** First run the *same* signed direct/iframe visual assertions against untouched public output for a specific missing-percent RED. With the new isolated signed snapshot, require 25/50/75% model-only geometry, accessibility and hit test, indeterminate non-download phases, Test queue/order, one model GET and one WASM GET, no unapproved origins, and verified bytes. Keep the project-owned checks in the normal `test:browser`; run `AEROBEAT_FRIEND_GAME_PROGRESS_DIR=.tmp/<new-signed-candidate> npm run test:friend-game-progress` for the default ≥6s hold and again with `AEROBEAT_FRIEND_GAME_PROGRESS_EXTENDED_SLOW_START=1` for ≥35s. Run tamper, truncation, one-quarter-transfer disconnect, repeat Play, and reconnect recovery. The browser test currently asserts 25/50/75 but **does not** capture a stable 100% DOM state, physical T-pose, scored contact or real-phone speed; either add a meaningful scoped browser assertion before claiming that state or explicitly leave it to unit and phone evidence. No approved UI mockup fidelity tier exists; these named DOM/geometry assertions are the actual normal visual gate. Add a Worker/vendor-owner test that records the **actual** model/WASM request order and non-overlap (which may be model-first for this approved progress-only design), and catches a duplicate GET or false `loaded`; compare the sequence openly with frozen production rather than claiming they are identical. Keep tests unchanged while removing only the new production behavior in an isolated counterfactual; the named visual case must fail for absent percentage, then pass when restored. Label any Browser 100% state honestly rather than claiming a screenshot the test cannot see.
4. **Do not waive the two existing release blockers.** A strict signed, same-request Browser/Worker run must show that the model GET completes without unexplained `ERR_ABORTED,canceled:true`, and the Worker sees EOF, exact length, SHA, one `loaded`, usable pose, and eventual audio-only Test. If a cancellation recurs, stop and diagnose it; do not suppress it in the test just because the game played once. Run the entire ordinary `npm test` and `npm run test:browser`, not just the passing suffix. The direct 390×844 DPR3 ≥15fps/35-render and strict <66ms p90 audio-timeline gates remain unchanged. If they fail, **NO RELEASE**: either repair a demonstrated source/environment cause and rerun the complete gate, or separately bring a tightly evidenced baseline-attributed exception to Derrick for an explicit decision. The earlier matched historical diagnostic is not that approval. Address the separate `tstv` ResourceTiming fixture bug only with real request-count proof; it cannot turn a cadence failure green.
5. **Signed staging, review, and human acceptance.** Build/sign only an isolated clean-source candidate; verify manifest, every asset's original decoded SHA, locked provenance, `npm run test:friend-game-static` and signed-served `scripts/validate-friend-game-browser.js` checks (including HEAD/identity/Brotli, CSP/404 and direct/iframe origins). Compare frozen signed localhost4200 control with the separately owned isolated candidate served only for QA; do not substitute an unserved Vite build for public route evidence. Independent QA then auditor review the exact candidate, test evidence, route isolation, release threats and the no-speed language. Keep the frozen live snapshot and full rollback. Obtain Derrick's Moto G Power 2024 and friend's Pixel 7a feedback on a separately approved private signed preview if their access permits; record first/repeat Play, visible model-only bar and queued Test, camera/calibration, audio, and any failed request. Do not call a private preview public verification or promise a faster startup. Only after all gates are green, phone feedback is acceptable, and Derrick gives a **separate public release GO**, atomically replace *only* `dist-friend-game` on the existing server. Compare HTTPS443/TLS/DNS, HTTPS10000 tester and ten existing private routes before and after; check original SHA and rollback readiness and immediately restore on a route/asset/security regression. Never start a replacement public server to make a local test look live.
6. **Documentation and closure.** Update assembly and linked-owner README text to say “pose model download” rather than startup progress or a speedup; describe indeterminate preparation, failures, and what 100% means. Record actual signed phone/public outcomes and remaining limitations in the approved plan and Beads. If no safe progress-only path passes strict request and browser gates, return the evidence for Derrick's decision instead of publishing.
