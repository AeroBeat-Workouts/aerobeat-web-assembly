## Debugging report before any code edits

**Exact observed symptom:** Derrick's physical 60-second CV window delivered 446 submitted frames / 447 pose outputs (~7.43–7.45/s), despite 29.775 fresh camera frames/s and near-60 scene FPS. In real scored Play he also sees <60 FPS and lagging CV; Test explicitly disables both camera and CV. These are two different workloads; neither proves the other's exact bottleneck.

**Expected behavior/question:** The diagnostic must distinguish worker-busy timer skips, no-new-camera-frame checks, main-thread frame preparation/transfer, Worker round-trip and inference/postprocessing, and completion-to-next-accepted-frame wait. It must quantify a current bottleneck, not claim a scheduling fix will reach 30/s. The unchanged 15/s cap and 80.9-ms median inference already preclude 30 pose outputs/s in this profile.

**Execution path:** `requestVideoFrameCallback` observes distinct camera frames in `phone-performance.js`; the CV service's 67-ms `setInterval` calls `estimate`; if `inFlight` is set it increments `droppedFrameCount`, else checks `isFrameAvailable`; an accepted frame reads timestamp, creates `VideoFrame`, calls `adapter.estimateNormalizedPoseFrame`, which posts a transfer to the Worker; synchronous `detectForVideo` and postprocessing return one result; service increments pose count; renderer independently continues scene ticks; recorder snapshots each 60-second run.

**Leading hypothesis, not established root cause:** An ~85-ms median estimate overlaps the next 67-ms tick, which is skipped; the following tick at ~134 ms would give ~7.46/s, near 7.43 measured. But reported medians do not prove tick timing, and timer jitter, occasional longer inference, unavailability, Worker handoff or warmup could change the accounting. No scheduler change until real skip counts and timings are obtained.

**Alternatives by likelihood:** (1) Fixed-timer aliasing, supported by 67-ms interval and 84.8-ms estimate, unconfirmed drops. (2) Additional main-thread `VideoFrame`/postMessage/Worker overhead or throttling, suggested by ~4-ms median estimate-minus-inference but percentiles cannot be subtracted per sample; measure paired stages. (3) No-new-frame admissions despite 30-fps capture, possible if rVFC stalls or frames arrive on an unfavorable schedule; count checks. (4) Thermal variation, impossible to infer from one run without repeated physical windows. Score/lease/calibration work is absent from this isolated test by design.

**Prior approaches:** The first diagnostic reports submitted/output counts and aggregate inference and estimate timings but omits busy drops, freshness checks and admission spacing. No scheduling fix was attempted. Assuming a faster model or merely raising the cap would not diagnose the observed timing; Lite is already the lightest MediaPipe profile Derrick chose.

**Unknowns and minimal reproduction:** Count in-window 67-ms timer attempts and busy drops via service status plus diagnostic source-check calls, after CV warmup. Run Game→Camera→CV Full 60s on the same phone with stable light/orientation/foreground. Record per-stage bounded summaries rather than individual timestamps. The project-owned 4-second synthetic camera only proves wiring and export, not physical throughput or heat.

**Proposed verification before optimization:** Expose run-local bounded counters/quantiles; assert count accounting and no metrics on Game/Camera; assert exactly one use of each fresh frame and proper reset on mode/quality/hidden retry. With the same browser tests, remove one key timing export in disposable stage and require an assertion to fail; restore and rerun. Contrast new phone data with the archived baseline without claiming identical thermal conditions.

**Recommended measurement-only change:** In diagnostic code retain the existing production service/Worker unchanged, observe cumulative `droppedFrameCount`, count freshness checks and admitted frames in the unique-source wrapper, time preparation and Worker estimate with a diagnostic-only adapter decorator, read existing vendor inference/postprocess/round-trip telemetry, and retain fixed-capacity scalar statistics. Keep per-stage labels precise; a round-trip remainder is *combined* transport/queue/preprocess, not uniquely transfer time. If reliable timer-attempt accounting or an exact segment cannot be observed from this page, label that segment unavailable rather than infer it. Use no frame/pixel/pose/device-ID export.

**Compact record:** Problem: 7.43 submissions/s vs 15/s timer ceiling. Observed: 60s physical CV ~7.45 pose/s; fixed 67-ms timer, ~85-ms median estimate. Root cause: not yet established; fixed-timer busy skips are leading hypothesis. Evidence: cited service path and prior scalar export. Failed approaches: none; old export lacked skip accounting. Corrective action: diagnostic-only bounded measurements, no runtime tuning. Verification: browser/paired stage counters, mutation proof, then Derrick's real phone JSON. Components: `src/phone-performance.js`, diagnostic helper/tests, read-only service/Worker telemetry. Remaining uncertainty: per-stage physical time and scored Play difference.
