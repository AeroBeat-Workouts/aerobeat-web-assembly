**Expected behavior/question:** The diagnostic must distinguish worker-busy timer skips, no-new-camera-frame checks, main-thread frame preparation/transfer, Worker round-trip and inference/postprocessing, and completion-to-next-accepted-frame wait. It must quantify a current bottleneck, not claim a scheduling fix will reach 30/s. The unchanged 15/s cap and 80.9-ms median inference already preclude 30 pose outputs/s in this profile.

**Execution path:** `requestVideoFrameCallback` observes distinct camera frames in `phone-performance.js`; the CV service's 67-ms `setInterval` calls `estimate`; if `inFlight` is set it increments `droppedFrameCount`, else checks `isFrameAvailable`; an accepted frame reads timestamp, creates `VideoFrame`, calls `adapter.estimateNormalizedPoseFrame`, which posts a transfer to the Worker; synchronous `detectForVideo` and postprocessing return one result; service increments pose count; renderer independently continues scene ticks; recorder snapshots each 60-second run.

**Leading hypothesis, not established root cause:** An ~85-ms median estimate overlaps the next 67-ms tick, which is skipped; the following tick at ~134 ms would give ~7.46/s, near 7.43 measured. But reported medians do not prove tick timing, and timer jitter, occasional longer inference, unavailability, Worker handoff or warmup could change the accounting. No scheduler change until real skip counts and timings are obtained.

**Alternatives by likelihood:** (1) Fixed-timer aliasing, supported by 67-ms interval and 84.8-ms estimate, unconfirmed drops. (3) No-new-frame admissions despite 30-fps capture, possible if rVFC stalls or frames arrive on an unfavorable schedule; count checks. (4) Thermal variation, impossible to infer from one run without repeated physical windows. Score/lease/calibration work is absent from this isolated test by design.

**Prior approaches:** The first diagnostic reports submitted/output counts and aggregate inference and estimate timings but omits busy drops, freshness checks and admission spacing. No scheduling fix was attempted. Assuming a faster model or merely raising the cap would not diagnose the observed timing; Lite is already the lightest MediaPipe profile Derrick chose.

**Unknowns and minimal reproduction:** Count in-window 67-ms timer attempts and busy drops via service status plus diagnostic source-check calls, after CV warmup. The project-owned 4-second synthetic camera only proves wiring and export, not physical throughput or heat.

## Debug record: failed estimate gap contamination (2026-10-10)

**Exact observed failure:** Independent QA reproduced helper-only: a success settled at 110 ms, failed estimate at 130 ms, then admission at 140 ms yields `completionToAdmissionMs=30` from the old success. No physical valid-window failure is established; production service normally transitions to error and invalidates this window.

**Expected behavior:** A failed estimate cannot leave an old successful completion as the predecessor of a later accepted admission. Export a gap only when a valid prior adapter completion directly precedes admission in the same window.

**Execution path/root cause:** `src/phone-performance-pipeline.js` `settled(ticket,...,error=true)` increments `estimateFailures` and returns without clearing `lastCompletionAt`; `admitted()` later subtracts this stale time. This is helper bookkeeping, not MediaPipe runtime or fixed timer behavior. Alternative: treating failed completion as timing baseline would measure a failure-to-next gap but mix failed and successful estimates; rejecting the gap is clearer.

**Why earlier tests missed it/unknowns:** Initial unit test asserts failure count and later reset but never admits again before reset. Browser happy-path Worker never fails midrun; the production error phase generally makes this a low-impact edge, yet retaining a false label is avoidable. Unknown whether a Worker can recover without a fresh mode selection; current service code does not resume on error.

**Minimal reproduction/verification/fix:** In the deterministic helper unit test, admit after a failure and assert no new `completionToAdmissionMs` sample; then reset and assert a fresh valid pair measures normally. Clear `lastCompletionAt` on error, preserving the `estimateFailures` count. A disposable-stage mutation restoring the bad behavior should fail that exact assertion while the fixed test passes. No production source modification.

**Compact record:** Problem: stale completion across failed estimate; observed symptom: false 30-ms idle gap; root cause: error path retains previous completion; evidence: QA helper reproduction; failed approach: success-only unit path; corrective action: clear completion on error; verification: same helper test with bug-specific mutation; related file: diagnostic-only pipeline helper; remaining uncertainty: whether real Worker failures occur during qualifying phone runs (such runs are invalid anyway).
