## Goal and scope

A user can type finite nonnegative decimal Boxing Depth + and Depth − values—including `0`, `0.00001`, `0.5`, `5` and `9999999`—and the saved value persists rather than reverting; the next Boxing run uses the stored value for its scored collider and Show overlay. Keep the existing Boxing **scale** limit `.25..4`, default front `1`/rear `3`, guard and reach behavior, Flow's separate profile, old stored values, and signed public 0.0.132 unchanged until publication approval. Extremely large rear depth may exceed the independent real audio duration limit of 86400 seconds; distinguish accepting a field from a genuinely representable scored Play timeline rather than silently clamp.

## Debugging report — before product code edits

### Exact observed failure and expected behavior

Derrick: “Boxing collider values keep reverting when I try to change the forward and backward depth floats, those should not be arbitrarily limited in any way, that would be a decision I make.” On the installed HTTPS443 signed 0.0.132, a runtime-only probe selecting the Boxing control mode (no product bytes changed) found input `min="1" max="4"`. Entering each of `0`, `0.00001`, `0.5`, `5`, `9999999` into either depth and dispatching the native `change` showed HTML validity false and reverted the displayed/saved value to front `1` or rear `3`. This was an installed-control check without a selected Boxer chart, not a scored phone playtest. Direct source import independently found `normalizeGameSetup` rejects each out-of-range value; `createBoxingColliderSettings` throws `Boxing Collider forward depth is outside its bounded range`; the flat Boxing contract rejects front <1 (and accepts >4). Baseline 1 and 4 are accepted by all three.

Expected: depth is a user-chosen nonnegative distance factor, both directions independently, without `.25..4` scale limits or `1..4` depth limits; reject nonfinite or negative values and preserve separate Boxer/Flow settings and run locks. Front/back defaults are not minimums.

### Execution path and cause

Game Setup builds both depth number inputs with min1/max4 in `src/index.js:3240`. `renderColliderVolumeControls` dynamically reattaches `colliderVolumeBounds` min/max for Boxing at line3264. The `change` handler at line3265 gates on `input.validity.valid`, then calls `setGameSetupSnapshot`; the invalid-input path redraws the old value. Even if DOM constraints are bypassed, `src/game-setup-coordinator.js:13,75` normalizes Boxing depth via `boundedNumber([1,4])`, so persistence also rejects it. Next-run `gameplayBoxingColliderSettings` feeds `@aerobeat/web-gameplay` `createBoxingColliderSettings` in `boxing-collider-collision.js:91-92`, where both depths are bounded `[1,4]`. Flat `@aerobeat/web-contracts` `isColliderSettings` imposes forward>=1 at `collider-contracts.js:33,126`, so resolving Boxer's scored bounds with front0 fails independently. The renderer consumes accepted depths to scale Show; the scored geometry and late deadline use the run-locked value. This is **multiple real limits across UI, storage, gameplay and contract**, not a browser-number-input bug alone.

### Alternatives, previous fixes, unknowns

A stale saved profile or run-locked session could also present previous values, but the fresh public control repro has invalid HTML and old value before starting a run. Browser step alone is not the sole cause: pure coordinator and gameplay validators also reject the same values. Previous 0.0.131/0.0.132 Flow changes intentionally kept Boxing's historical limits separate; no previous Boxing-depth fix was attempted. Unknown: exact values Derrick tried, whether his phone keyboard produces a different edit sequence, and whether enormous rear values should be *playable* despite the separate real 86400-second audio-clock capacity. `src/scoring-clock-minimum.js:39-44` throws when the chart's scored deadline exceeds that physical limit; do not claim all finite depths can complete Play. Inspect the release candidate's native Boxer session for moderate out-of-range values and test storage reload plus scored visual parity to resolve user impact; ask Derrick if he later needs a specific extreme value that exceeds the truthful clock limit.

**Post-release probe timing:** An initial diagnostic script dispatched `change` and then forcibly called `renderColliderVolumeControls()` in the same task immediately after blur. It transiently redisplayed the old in-memory `desiredGameSetup` even though localStorage had already saved the correct new value; the production subscription applies setup through an asynchronous lifecycle queue (`src/index.js:374`). Waiting for that queued sync before reading the displayed value showed all tested depths retained and survived reload. This was a probe race caused by manual premature rendering, not a remaining product reversion; real signed native scored Play tests waited for the committed lifecycle.

### Minimal reproduction and proposed verification

Install the unchanged 0.0.132 build, display Boxing Game Setup and enter forward `0.5` or backward `5`; on `change`/blur, the number resets to the old 1/3. A programmatic one-session fresh-page probe gave the same result for zero, tiny and 9999999; the mode-selection override used only in the probe means a full native Boxer chart flow still needs checking. Probe with valid `1` and `4` does not reset. Build a focused regression using the existing real Boxer setup browser harness and native controls (direct + genuine iframe); assert display, saved storage and next-run locked profile for representative small/large finite depths, plus Show/scored boundary shift. Source unit checks should cover gameplay contract, settings identity and finite/nonnegative rejection. First establish RED on frozen signed old build (or unchanged source); then new source GREEN and independently reviewed immutable signed successor if publication is authorized.

### Recommended fix and risks

In assembly, remove min/max **only for Boxing depth inputs** except `min=0`, keep Boxing scale `.25..4`, and validate the two depths by finite nonnegative type independently of scale. In the gameplay owner remove only the two depth `[1,4]` guards while preserving other Boxer fields; in contracts let flat Boxing settings forward be nonnegative to admit a zero-thickness front extent. Add regression coverage for storage roundtrip, native UI, run-locked and scored/Show paths; do not relax global audio duration or widen Flow/notes. Preserve finite arithmetic checks and flag any demonstrated overflow as a separate representability issue rather than introducing another arbitrary silent clamp.
