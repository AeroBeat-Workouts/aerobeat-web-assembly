## Debug diagnosis before implementation

**Exact observed failures:** Derrick saw only model-stage growth to `32%`, then no visible WASM updates or `100%` before calibration. During phone Flow, blue “Good” sometimes appeared on unsliced notes. We have no per-note phone recording; the latter's precise event ID/persistence is unknown.

**Expected:** Actual decoded download bytes should move the existing one bar while the selected WASM transfers, with the same bare number and no time-based filler; calibration is separate. For Flow, the newly approved rule is: an early near pass stays pending, subsequent real contact earns Great/slice, otherwise yellow Almost/50/combo appears only when Miss normally commits.

**Execution paths and likely root causes:** Worker `/vendor-mediapipe/src/mediapipe-worker.js` streams verified model bytes into the facade/UI, but pinned classic Tasks Vision 1.0.1 itself calls `fetch(binaryFile,{credentials:"same-origin"})` inside its Emscripten loader and passes that Response directly to `WebAssembly.instantiateStreaming` (`node_modules/@mediapipe/tasks-vision/wasm/vision_wasm_internal.js:330–345`); it exposes NO supported partial-byte callback. Worker adds full runtime bytes only after `PoseLandmarker.createFromOptions`, immediately followed by `loaded`; assembly stops the 100ms integer-percent watcher as CV becomes ready and the bar disappears (`src/index.js:3142–3171`). Independently, gameplay `session-coordinator.js:1375–1401,1763–1767,1822–1833` commits a qualifying near pass immediately as `result:"miss",tier:"good"`, scoring 50 and marking the event judged; a subsequent true slice is therefore blocked. Assembly forwards Good and renderer displays blue Good with an intact unsliced note (`session-render-projection.js:140–146`; renderer `gameplay-scene-model.js:336–356`). This last mechanism is proven by current code/tests; attribution to Derrick's specific note remains uncertain.

**Alternative hypotheses and uncertainties:** Phone WASM may have compiled after its bytes completed, but does not explain no partial percentage; page ResourceTiming reports only completed response and Brotli `Content-Length` is compressed, not decoded. Re-fetching WASM gives artificial progress but duplicates a large GET. Tasks Vision uses native fetch/`instantiateStreaming`; HTTP XHR listeners would not see it. A worker-scoped `fetch` wrapper plus pass-through `TransformStream` could *in principle* count decoded bytes from the existing one Response with backpressure, but it replaces the native Response object, may affect streaming compilation/cancellation or loader fallback (the pinned loader may re-fetch on failure), and is not a supported vendor API; **not yet shown safe**. An independent visual/FX problem for a true Great hit remains possible but is not required to explain blue Good on intact notes. Missing fact: whether that exact phone note persisted vs vanished. Full renderer cadence still has the documented headless RED; browser model-request `ERR_ABORTED` remains unexplained. Neither is a valid shortcut to claim safety.

**Why earlier fixes do not solve this:** The previous buffering fix verified the model GET before WASM, and denominator fix intentionally prevented early 100 but had no WASM byte feed; the one-bar UI clears at ready. The earlier near-miss design intentionally rewarded noncontact as Good (explicit obsolete project tests), so an animation-only fix would not let a later real slice supersede it.

**Minimal reproductions and proposed verification:** Existing signed direct 390×844 game gate holds the complete real WASM body for six seconds: it consistently shows native `32%`, then proceeds to calibration with no asserted visible 100. Replace ONLY the isolated browser fixture's WASM hold with one signed 25/50/75% incremental same-request response for an old-build **RED** on absent asset-phase updates; a candidate must pass monotone decoded-byte/percent visual assertions, exactly one selected WASM GET, no extra text, no calibration counted, and normal Play/Test success. Existing gameplay `scripts/validate-gameplay-session.js:292–345` explicitly makes near noncontact Good/50 immediately; new test must fail old code for premature judgement and pass when a later contact supersedes with Great/slice, or when the normal Miss boundary yields Almost/50/combo. Renderer/assembly normal browser pixel gates must assert actual spelled yellow Almost and no slice on near, plus two halves for a real contact. No public swap on a RED candidate.

**Recommended fixes (conditional):** First run the signed WASM-chunk RED gate. Try a vendor-worker-only scoped one-GET decoded-byte pass-through only in an isolated build, with strict no-extra-memory/backpressure, identical `application/wasm`, response/cancellation/fallback guard and phone-relevant browser proof; abort if it changes semantics or requires duplicate GET. Flow's directly approved policy is a pending near-candidate record cleared on a real contact and finalized only at the existing miss boundary as `miss/almost`, with renderer yellow Almost glyph/pixel support; preserve non-Flow scoring. Keep public build unchanged until each boundary has exact source-pinned tests; release lanes separately unless Derrick asks to combine.
