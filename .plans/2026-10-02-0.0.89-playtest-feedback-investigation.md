## Performance measurement — CONFIRMED on real GPU (cookie, RTX 3080, 2026-10-03)

Derrick confirmed the WarioWare regression is **constant from the start of the song** (not accumulation). Measured on this machine with the REAL WarioWare map (`1bb8`, 2602 notes / 214 obstacles / 19 min Hard) converted through the real content pipeline (3089 flow beats / 1223 boxing beats), live 0.0.89 app, headless Chromium using the **real RTX 3080** (`ANGLE (NVIDIA GeForce RTX 3080, OpenGL 4.5.0)`), 1280x720, seeking to the dense 6-minute section, 30 s windows:

| Metric | Flow | Boxing |
|---|---|---|
| fps avg | **52.5** | **58.2** |
| rendererCpuMs p50 | 2.3 ms | 1.7 ms |
| scene objects | **57** | **37** |
| PlayCanvas drawCalls | **85** | **53** |

**Findings:**
1. The Flow discriminator reproduces on real GPU: Flow ~6 fps slower than Boxing on the same song.
2. Flow renders 57 objects / 85 draw calls vs Boxing 37 / 53 — ~50% more objects, ~60% more draw calls. The per-object cost is icon + shadow (+ feedback); shadows are ~half the draws.
3. Even on an RTX 3080, Flow does not reach 60 fps (52.5) — on the weaker glitch-machine GPU this is the "terrible" performance.
4. JS is negligible (2.3 ms p50) — confirms the regression is GPU draw-call cost, constant per frame (matches "bad from the start").
5. Spawning is NOT at start: only the live lead-window (~57 objects) is in the scene; PlayCanvas entities are pooled. A 19-min song has the same per-frame scene size as a 3-min song.

**Recommended fix (measurable with this same harness):** distance-cull note shadows (skip shadow objects beyond a Z depth where visually irrelevant) + drop obstacle shadows (walls are opaque glass; their shadow quad buys little). Renderer-only change in `gameplay-scene-model.js`; expected to cut Flow draw calls from ~85 toward the ~53 Boxing baseline. Fallback if insufficient: batch all shadows into one merged draw call.

Harness: `/tmp/aero-perf/wario-gpu-profile.mjs` (real-GPU, real map, Flow vs Boxing, seekable). Map archive: `/tmp/wario/map.zip`.

## GPU probe suite — shadow hypothesis DISPROVEN on cookie (2026-10-03)

Derrick asked for probes to determine the exact regime (batching/draw-call vs transparency/overdraw) before choosing the perf fix. Ran on cookie (RTX 3080), real WarioWare Flow dense section, real GPU headless Chromium, with warm-up controls. Key infrastructure finding: the bundled PlayCanvas fires `postrender` (NOT `postframe`); scene tree root is `app.root` (scene.root is null); shadow entities are named `:shadow:` (16 live).

**Warm-up controlled results (720p dpr1, 25 s windows):**

| Config | fps |
|---|---|
| A1 baseline (first run of session) | 52.0 |
| C shadows off (16 disabled, verified) | 58.0 |
| A2 baseline (after C) | **58.8** |
| D shadows opaque (blend OFF) | 59.1 |
| A3 baseline (after D) | **59.3** |

**The +7 fps "shadow effect" was a first-run warm-up artifact** (shader compilation / driver warm-up per browser session) — baselines after the shadow configs match the shadow-removed configs. **Shadows on/off/opaque make no measurable difference at steady state.** The earlier "52 vs 58" readings were order effects, not shadow cost.

**Resolution ladder (dpr1) on the 3080 — flat:** 1280x720 = 57.9, 1920x1080 = 58.7, 2560x1440 = 59.1, **3840x2160 = 59.3**, 1920x1080 dpr2 (8.3 Mpx) = 59.4 fps. The scene (57 objects, 85 draw calls) is GPU-light: the 3080 is vsync-limited at every resolution up to 4K. **No transparency/overdraw/batching problem is measurable on cookie at any reasonable resolution.**

**Conclusions:**
1. The shadow/transparency art-style change is NOT supported by cookie measurements — do not pursue it as the perf fix.
2. Real finding: **per-browser-session warm-up cost** — first session ~52 fps, subsequent ~59 fps (one-time shader compilation). Candidate for a shader pre-warm at app load if the first-song experience matters.
3. The glitch-machine regression is **not reproducible on the 3080 at any resolution** — its bottleneck is not visible from cookie. Glitch is **Windows on ARM** (arm64 Python detected, no Node.js, Chrome present) — a much weaker iGPU regime. The same probe suite must run ON glitch to identify its bottleneck (needs a Node.js install there — pending Derrick's OK), or a DevTools Performance capture on glitch (Rendering vs Scripting in the frame grid).

Harness: `/tmp/aero-perf/wario-probes.mjs` (portable; configs swappable). Map: `/tmp/wario/map.zip`.

## Glitch-machine probe suite — shadow hypothesis DISPROVEN on the failing hardware (2026-10-03)

Ran the same probe suite ON the glitch machine (Derrick approved: Node.js LTS arm64 installed via winget, Playwright with system Chrome, app served from disk via Playwright route interception because the fleet machine blocks loopback HTTP even from its own PowerShell).

**Resolution ladder on glitch (ARM iGPU) vs cookie (RTX 3080):**

| Resolution | cookie fps | glitch fps |
|---|---|---|
| 1280x720 | 57.9 | 29.5 |
| 1920x1080 | 58.7 | 28.3 |
| 2560x1440 | 59.1 | 25.1 |
| 3840x2160 | 59.3 | 21.7 |
| 1080p dpr2 (8.3 Mpx) | 59.4 | 19.0 |

**The glitch GPU scales with pixel count** (fragment/fill-bound); the 3080 is vsync-flat. This is the regime the weak GPU was suspected to be in.

**Shadow transparency matrix on glitch (720p, warm-up controlled):**

| Config | fps |
|---|---|
| A1 baseline (first) | 23.9 |
| C shadows off (16 disabled, verified) | 29.8 |
| A2 baseline (after C) | **30.7** |
| D shadows opaque | 31.0 |
| A3 baseline (after D) | **31.3** |
| E all alpha-blended off (35 disabled) | 31.6 |
| A4 baseline (after E) | **31.8** |

**Steady-state on the failing hardware: shadows on/off/opaque/all-transparent-off all perform identically (~31 fps).** The +6 fps again is the first-run warm-up artifact (shader compilation per browser session), not shadow cost.

**Final perf conclusions (both machines, warm-up controlled):**
1. **Shadows/transparency are NOT the cost** — zero steady-state effect on the RTX 3080 or the ARM iGPU. The art-style change (no shadows / no transparency) is NOT the fix. Do not pursue it.
2. **The glitch machine is generally fragment/fill-bound**: fps scales linearly with pixel count (29.5 @720p → 19 @4K); even with all transparency removed it does not improve. The fill cost lives in the whole scene (additive note quads blendType=3, full-screen photosphere, tracks), not in alpha shadows.
3. **The effective fix for weak GPUs is render-resolution scaling** (dpr cap / quality setting): on a fragment-bound GPU this is the one knob that halves the fragment cost. E.g. rendering at 0.5x scale should roughly double fps on the ARM iGPU.
4. Secondary finding: **per-browser-session warm-up cost** (first session ~24 fps on glitch / ~52 on cookie → ~31 / ~59 after shader compile) — candidate for shader pre-warm at app load if first-song experience matters.
