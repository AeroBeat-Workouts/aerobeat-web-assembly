## Debugging record — diagnosis before product edits

**Exact observed failure:** Two real Pixel Chrome users see Android camera indicator after Play, but hear no Faint playback and see no status/error for about 30–60 seconds; pressing Test appears inert until one phone suddenly enters Test. The prior signed browser oracle only waited for eventual real fake-camera CPU Worker, not startup latency or the pending UI. In a read-only, controlled signed-localhost Chromium mobile repro, a 35-second delay on just the WASM GET produced a live camera at 0.865 s, CV `loading` and Play `pending` at 1.872 s, Test `pending` at 1.885 s with **unchanged visible button/info text**, WASM completion 35.960 s, model completion 36.080 s and Test `playing` at 37.094 s. That is directly observed; the phones' per-stage timestamps remain unknown.

**Expected behavior:** Downloaded Faint's Play should visibly acknowledge camera/pose initialization and not look inert while required files download. Test tapped during Play initialization must visibly acknowledge its queue and eventually start in a deterministic, safe order (or an explicitly approved cancellation policy); do not pretend audio should play before native calibration. A real error should surface and restore retry. The public signed browser gate should detect a missing startup indicator in slow network conditions, not merely eventual success.

**Execution path:** `src/index.js:3083-3097` Start/Test handler awaits serialized `startSession` and only closes the menu after completion. `:468-553` sets pending flags then awaits transport/audio tails, camera request and video play, `startCv`/`production-cv-service.js:38-49`/`web-vendor-mediapipe/src/mediapipe-worker-adapter.js:193-229`; classic Worker `mediapipe-worker.js:34-60` resolves WASM and then Lite model before acknowledging. Only then does gameplay requestStart/commit initial audio and clear pending. Test is audio-only but its lifecycle intent waits behind the in-flight Play action. Presenter `aerobeat-web-ui/src/elements/aero-product-presenters.js:550-560` reports pending through invisible `aria-busy` only; `src/index.js:2675-2694` runtime info/message ignores pending state.

**Most likely root cause:** The released static server transmits large local MediaPipe assets raw with `Cache-Control: no-store`. Real verified public Funnel relay transfers measured **11,756,954 B CPU WASM in 54.81 s** and **5,777,746 B Lite task model in 42.75 s** (separate probes, not a simultaneous phone trace); the Worker requires these sequentially. The local 35-second isolated WASM delay reproduced the *same visible Play silence and deferred Test*. Offline Brotli quality-4 of the exact signed bytes shrinks WASM to 3,124,166 B (27%, 278 ms to encode once), task to 4,970,278 B (86%, 54 ms), and game JS from 3,035,624 B to 753,189 B. This strongly explains the observed delay and invisible status. It does **not** prove each Pixel's actual network timing or eliminate a later calibration/audio problem.

**Alternative hypotheses, ranked:** (1) Camera video.play delayed: Pixel indicator alone does not prove play; controlled fake camera played by 0.865 s, so not this controlled repro, still possible physically. (2) Prior chart selection/audio decode or menu pause tail: preview uses separate HTMLAudioElement, not WebAudio; controlled fixture was content+audio ready at 0.805 s, so not its stall. (3) Worker error/hang: eventual Test and successful local worker falsify a permanent failure in that repro, but phone logs are absent. (4) Post-CV native calibration/audio gating: Play intentionally keeps music paused during calibration `src/index.js:558-565`; it may affect *when* song starts after transfer, but cannot explain the reproduced silent pending UI and queued Test while CV is `loading`.

**Why earlier fixes/tests missed it:** The previous release's signed oracle validated final CPU Worker state on fast loopback with fake camera and did not throttle model/WASM or assert pending text, while README warned first load could take minutes. The earlier Cookie device without a webcam was unrelated; the two Pixel Chrome reports are real. No speculative product fix has yet been attempted for this regression.

**Unknowns/minimal reproduction/proposed verification:** Physical Pixel exact camera/Worker/network/calibration timestamps and browser WASM variant remain unknown; a future real-phone retest can resolve these. Minimal repro: signed normal game on localhost4200, a playable in-memory project-owned ZIP, mobile Chromium/fake camera, delay only the same-origin WASM GET by 35 s, tap Start then Test, observe live camera and `cv.loading` but no visible acknowledgement until Test starts after delay.
