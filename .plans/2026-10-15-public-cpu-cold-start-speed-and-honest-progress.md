## Evidence and bounded hypotheses

- The Play action awaits camera/video then CV Worker initialization before starting game audio; Test is ordered behind Play. MediaPipe's classic Worker imports Vision JS, awaits WASM resolution, constructs the model-backed Pose Landmarker, then sends only one `loaded` acknowledgment (`src/index.js`, `src/production-cv-service.js`, linked `aerobeat-web-vendor-mediapipe/src/mediapipe-worker.js`). No download-percent callback exists today.
- The current server SHA-verifies its 55-asset frozen snapshot and sends Brotli for JS/WASM/model, but marks every asset `Cache-Control: no-store` (`scripts/serve-friend-game.js`). Public edge probes transferred WASM (~3.12 MB) in 16–20 seconds and model (~4.97 MB) in 20–24 seconds **separately**, not in a simultaneous Android trace. Browser loopback is not a phone benchmark.
- Candidate 1: compare read-only cold and repeat loads, then benchmark versioned, hash-pinned immutable asset caching in an **isolated signed build**, keeping HTML fresh. This can speed *repeat visits*, not the first ever transfer; changing cache headers on today's unversioned fixed asset paths is unsafe for stale-tab/release/rollback behavior.
- Candidate 2: measure an isolated **supported single-fetch model-buffer** Worker variant. The pinned Tasks Vision 1.0.1 public type accepts `baseOptions.modelAssetBuffer: Uint8Array` instead of `modelAssetPath` (`aerobeat-web-vendor-mediapipe/node_modules/@mediapipe/tasks-vision/vision.d.ts:17-29,2528-2548`). A Worker-owned streamed model fetch could count received *decoded* bytes and feed that exact buffer to `createFromOptions`, potentially overlapping the separate WASM resolver load. Compare Play→Worker-ready against current sequential behavior while checking exactly one model request, same pose/delegate, bytes/memory/cancel/error and chart/audio contention. Do not claim overlap speeds up phones before a controlled benchmark and physical retest. Separate prefetch-before-Play is lower priority because it may only shift wait earlier and waste traffic/CPU when friends never play.
- Progress candidate: display **model-download-only** percentage when actual received *decoded* bytes can be compared with the independently pinned decoded model byte size, labeled e.g. “Loading pose model: 43%”; no total startup percentage and no WASM percent. A compressed HTTP `Content-Length` is the **Brotli wire size**, while Fetch stream chunks are decoded: never divide one by the other. The public `FilesetResolver.forVisionTasks` accepts WASM *paths*, not pre-fetched binary bytes (`vision.d.ts:782-792,2891-2900`), so a WASM percent could duplicate the request or require unsupported internals. Show visible indeterminate “Preparing tracker…” before/after model transfer and ordinary calibration cues. Validate identity/Brotli exact byte parity, model error/cancel paths, frame-level progress throttling and no private CV change in an isolated fixture before product code; if this supported path fails, return with evidence instead of faking progress.
